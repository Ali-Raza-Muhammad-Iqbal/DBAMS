7.1 Physical Database Design — Overview

Definition

Physical database design is the process of translating a logical database design (tables, keys, relationships) into the physical structures that the DBMS actually stores on disk. It decides how data is stored and accessed — indexes, file organizations, partitions, compression, storage engines, and hardware layout.

It's the layer where performance and cost trade-offs get real. Two logical designs that are functionally identical can perform 1000× differently depending on the physical design.

Key Decisions in Physical Design

  • File organization — heap, sequential, indexed, hashed (Module 4.2).
  • Indexing strategy — which columns, what type (B+ tree, hash, composite, covering).
  • Partitioning — split large tables by range/hash/list for manageability and speed.
  • Storage engine — InnoDB vs MyISAM (MySQL), heap vs columnar (PostgreSQL, Redshift).
  • Compression — page-level or column-level; trades CPU for I/O.
  • Buffer pool size — how much RAM to dedicate to caching pages.
  • Storage layout — SSD vs HDD, RAID level, filesystem, cloud storage tier.
  • Tablespaces / filegroups — where files sit, which disk arrays.

Diagram — Where Physical Design Fits

Figure 7.1 — Physical design fits between logical design and physical hardware

Syntax — Physical design decisions in SQL

SQL — Physical design choices 
-- 1. Choose storage engine (MySQL)
CREATE TABLE Orders (
    OrderID    INT PRIMARY KEY,
    CustomerID INT,
    OrderDate  DATE,
    Total      DECIMAL(10,2)
) ENGINE = InnoDB;                 -- supports transactions, FKs

-- 2. Add an index on a frequently filtered column
CREATE INDEX idx_orders_cust ON Orders(CustomerID);

-- 3. Partition by range (MySQL 8)
ALTER TABLE Orders
    PARTITION BY RANGE (YEAR(OrderDate)) (
        PARTITION p2023 VALUES LESS THAN (2024),
        PARTITION p2024 VALUES LESS THAN (2025),
        PARTITION p2025 VALUES LESS THAN (2026)
    );

-- 4. Enable compression on a table (MySQL InnoDB)
ALTER TABLE Orders ROW_FORMAT = COMPRESSED KEY_BLOCK_SIZE = 8;

-- 5. Place the table in a specific tablespace (MySQL)
CREATE TABLESPACE ts_fast ADD DATAFILE 'fast_ssd.ibd'
    ENGINE = InnoDB;
ALTER TABLE Orders TABLESPACE ts_fast;

-- 6. Point a PostgreSQL table to a fast disk tablespace
CREATE TABLESPACE ts_fast LOCATION '/mnt/ssd/pg_fast';
ALTER TABLE orders SET TABLESPACE ts_fast;

-- 7. Set a per-table storage parameter (PostgreSQL)
ALTER TABLE orders SET (autovacuum_enabled = on, fillfactor = 90);
Simple Example

Logical design: an Orders table with OrderID, CustomerID, OrderDate.

Physical design: store it on an SSD tablespace, use InnoDB (for transactions), add an index on CustomerID (frequent filter), partition by year (for manageability), enable compression (for storage savings).

Real-Life Use Case

An e-commerce database has 500 million order rows. Without physical design: every query scans the full table (minutes). With physical design: partition by month → query "orders from last month" touches only 1 partition; add index on CustomerID → "orders for customer 123" → single index seek in milliseconds. Same logical schema, 1000× faster.

7.2 Mapping Logical Design to Physical Design

Definition

Mapping is the step-by-step translation from the logical schema (tables, keys, relationships) into concrete physical constructs (files, indexes, partitions, storage attributes). Each logical object becomes one or more physical objects.

Standard Mapping Rules

  1. Entity → Table — each logical entity becomes a physical table.
  2. Attribute → Column — each attribute becomes a column with a chosen data type and size.
  3. Primary Key → PK constraint + clustered index (in InnoDB, the PK is the clustered index; in PostgreSQL it's a unique B+ tree).
  4. Foreign Key → FK constraint + non-clustered index (add an index on the FK column for join performance).
  5. 1:1 relationship → Shared PK or unique FK between the two tables.
  6. 1:N relationship → FK on the "many" side + index on the FK column.
  7. M:N relationship → Junction (link) table with two FKs + a composite PK.
  8. Subtype/supertype → Shared table with nullable columns OR separate tables with a shared PK.
  9. Frequent lookups / filters → Index on the relevant column(s).
  10. Very large tables → Partitioning by date, hash, or range.

Diagram — Logical to Physical Mapping

Figure 7.2 — Logical ER mapped to physical tables with indexes and FKs

Syntax — Logical → physical in SQL

SQL — Physical mapping 
-- LOGICAL: Customer (1) ─── places ──→ Order (N)

-- PHYSICAL: parent table with PK
CREATE TABLE Customers (
    CustomerID INT AUTO_INCREMENT PRIMARY KEY,
    Name       VARCHAR(100) NOT NULL,
    Email      VARCHAR(150) UNIQUE
) ENGINE = InnoDB;

-- PHYSICAL: child table with FK + index on FK column
CREATE TABLE Orders (
    OrderID    INT AUTO_INCREMENT PRIMARY KEY,
    OrderDate  DATE NOT NULL,
    Total      DECIMAL(10,2) NOT NULL,
    CustomerID INT NOT NULL,
    CONSTRAINT fk_orders_customer
        FOREIGN KEY (CustomerID) REFERENCES Customers(CustomerID)
        ON DELETE RESTRICT
) ENGINE = InnoDB;

-- Index on FK for fast "orders for customer X" lookups
CREATE INDEX idx_orders_customer ON Orders(CustomerID);

-- Index on OrderDate for range queries ("orders in January")
CREATE INDEX idx_orders_date ON Orders(OrderDate);

-- Partition by year for a very large orders table
ALTER TABLE Orders
    PARTITION BY RANGE (YEAR(OrderDate)) (
        PARTITION p2023 VALUES LESS THAN (2024),
        PARTITION p2024 VALUES LESS THAN (2025),
        PARTITION p2025 VALUES LESS THAN (2026),
        PARTITION pmax  VALUES LESS THAN MAXVALUE
    );

-- For a M:N relationship (e.g., students ↔ courses), create a junction:
CREATE TABLE Enrollments (
    StudentID INT,
    CourseID  INT,
    Grade     CHAR(2),
    PRIMARY KEY (StudentID, CourseID),
    FOREIGN KEY (StudentID) REFERENCES Students(StudentID),
    FOREIGN KEY (CourseID)  REFERENCES Courses(CourseID)
);
Simple Example

Logical: "A Customer places many Orders."

Physical mapping:

1. Customer entity → Customers table (PK = CustomerID).

2. Order entity → Orders table (PK = OrderID).

3. "places" 1:N relationship → CustomerID FK in Orders.

4. Add index on CustomerID → fast lookups of "all orders for customer X".

Real-Life Use Case

A banking database starts with an ER diagram (Customer, Account, Transaction). During mapping: Customer → customers table with PK; Account → accounts table with FK to customers; Transaction → transactions table partitioned by month. Indexes on customer_id and account_id make "show me my recent transactions" queries return in milliseconds instead of scanning 10 million rows.

Physical Naming Conventions

Common patterns: tables in snake_case (PostgreSQL style) or PascalCase (SQL Server style); index names like idx_table_column; FK names like fk_child_parent. Consistent naming makes debugging and audits far easier.

7.3 Denormalization and Its Trade-offs

Definition

Denormalization is the deliberate reversal of normalization — introducing redundancy or merging tables to speed up reads. It's a physical design decision, not a logical one: the schema is intentionally less "clean" but queries are much faster.

Rule of thumb: normalize for OLTP (writes), denormalize for OLAP (reads).

Techniques of Denormalization

  • Precomputed aggregates — store TotalSales in Customer instead of SUM-ing orders every time.
  • Redundant columns — copy CustomerName into Orders to avoid a join.
  • Merged tables — collapse a 1:1 relationship into one table.
  • Star schema / snowflake schema — data-warehouse patterns where dimensions are denormalized for fast analytics.
  • Materialized views — store the result of a complex query.
  • Summary tables — pre-built aggregates for dashboards.
  • Replicated reference data — duplicate lookup tables (countries, categories) in each database.

Trade-offs — The Big Comparison

AspectNormalized (3NF+)Denormalized
Read speedSlower (needs JOINs)Fast (fewer JOINs)
Write speedFast (small tables)Slower (must update redundancy)
StorageMinimal (no duplicates)More (repeated data)
Data consistencyGuaranteed (single source)Needs care (updates everywhere)
Update anomaliesNoneRisk if not maintained carefully
Schema complexityMany small tablesFewer, wider tables
Best forOLTP (banking, booking)OLAP (reporting, analytics)

Diagram — Normalized vs Denormalized

Figure 7.3 — Normalized (many tables, joins) vs Denormalized (wide table, no joins)

Syntax — Denormalization in action

SQL — Denormalized schema 
-- Denormalized table: fewer joins, faster reads
CREATE TABLE Orders_Flat (
    OrderID         INT PRIMARY KEY,
    OrderDate       DATE NOT NULL,

    CustomerID      INT NOT NULL,
    CustomerName    VARCHAR(100),      -- duplicated from Customers
    CustomerEmail   VARCHAR(150),      -- duplicated from Customers

    ProductID       INT NOT NULL,
    ProductName     VARCHAR(200),      -- duplicated from Products
    UnitPrice       DECIMAL(10,2),     -- duplicated (price at sale time)
    Quantity        INT,

    Total           DECIMAL(10,2)      -- precomputed = UnitPrice × Quantity
);

-- Query without any JOIN — very fast:
SELECT CustomerName, OrderDate, ProductName, Total
FROM Orders_Flat
WHERE OrderDate >= '2025-01-01';

-- Maintained with a trigger (so duplicates stay in sync)
DELIMITER $$
CREATE TRIGGER trg_orders_flat_sync
AFTER UPDATE ON Customers
FOR EACH ROW
BEGIN
    UPDATE Orders_Flat
    SET CustomerName = NEW.Name, CustomerEmail = NEW.Email
    WHERE CustomerID = NEW.CustomerID;
END$$
DELIMITER ;

-- Materialized view (PostgreSQL) — denormalized cache of a query
CREATE MATERIALIZED VIEW order_summary AS
SELECT c.CustomerID, c.Name,
       COUNT(o.OrderID) AS OrderCount,
       SUM(o.Total) AS TotalSpent
FROM Customers c
LEFT JOIN Orders o ON o.CustomerID = c.CustomerID
GROUP BY c.CustomerID, c.Name;

-- Refresh periodically
REFRESH MATERIALIZED VIEW CONCURRENTLY order_summary;
Simple Example

Normalized: querying "orders with customer names" requires JOIN Customers ON Orders.CustomerID = Customers.CustomerID — 2 tables, moderate speed.

Denormalized: CustomerName is copied into Orders — no JOIN, extremely fast read. But if a customer renames, you must update every order row.

Real-Life Use Case

Amazon keeps product data normalized for writes (product catalog), but its product-search index and analytics warehouses are heavily denormalized — search results and dashboards must return in milliseconds. Data warehouses like Snowflake, BigQuery, Redshift use star schemas (heavily denormalized) because the goal is fast analytical queries, not transaction safety.

Don't Denormalize Prematurely

Start with a normalized schema. Only denormalize when you have evidence (via query profiling) that JOINs are the bottleneck. Denormalizing too early creates maintenance headaches (triggers, sync issues) without commensurate benefit.

7.4 Performance Tuning — Query Optimization

Definition

Query optimization is the process of finding the most efficient way to execute a SQL query. It's done at two levels:

  • Automatic (DBMS): the optimizer analyzes the query, uses statistics, and picks the cheapest execution plan.
  • Manual (DBA/Developer): rewriting queries, adding indexes, adjusting config — based on the execution plan.

Both are essential. The best optimizer can't help a badly written query; the best-written query can't help a badly designed index.

What the Optimizer Does

  1. Parse — check syntax.
  2. Validate — confirm tables/columns exist, check permissions.
  3. Rewrite — apply algebraic rules (push WHERE down, eliminate redundant subqueries, constant folding).
  4. Plan — generate candidate plans (which join order, which access method, which index).
  5. Cost — estimate cost of each plan using statistics.
  6. Choose — pick lowest-cost plan.
  7. Execute — run the plan.

Common Tuning Techniques

  • Analyze the execution plan — EXPLAIN / EXPLAIN ANALYZE / SHOW PLAN.
  • Avoid SELECT * — fetch only needed columns.
  • Filter early — use WHERE instead of filtering after a JOIN.
  • Use appropriate indexes — on columns in WHERE, JOIN, ORDER BY.
  • Avoid functions on indexed columns — WHERE YEAR(date) = 2024 can't use a date index; use range: WHERE date BETWEEN '2024-01-01' AND '2024-12-31'.
  • Prefer EXISTS over IN for large sets.
  • Batch operations — insert 1000 rows in one statement, not 1000 statements.
  • Use LIMIT for pagination — don't fetch 1M rows to display 20.
  • Keep statistics updated — run ANALYZE / UPDATE STATISTICS.
  • Avoid N+1 queries — fetch related data in one JOIN, not per row.

Diagram — Reading an Execution Plan

Figure 7.4 — BAD: full table scan (2.5s) vs GOOD: index seek (3ms) — 830× difference

Syntax — Analyze and optimize

SQL — EXPLAIN + tuning 
-- 1. SEE THE PLAN
EXPLAIN SELECT * FROM Orders WHERE CustomerID = 100;
-- MySQL output key columns:
--   type: ALL (full scan) vs ref/range/const (fast)
--   key:  NULL (no index) vs idx_orders_customer
--   rows: 10,000,000 vs 50 (rows examined)

-- PostgreSQL — with actual runtime stats
EXPLAIN ANALYZE SELECT * FROM Orders WHERE CustomerID = 100;
-- Look for: Seq Scan (bad) vs Index Scan (good)

-- SQL Server — actual plan
SET STATISTICS PROFILE ON;
SELECT * FROM Orders WHERE CustomerID = 100;

-- 2. REWRITE BAD QUERIES
-- BAD: SELECT * — fetch only what you need
SELECT * FROM Orders WHERE CustomerID = 100;

-- GOOD: fetch specific columns
SELECT OrderID, OrderDate, Total FROM Orders WHERE CustomerID = 100;

-- BAD: function on indexed column → can't use index
SELECT * FROM Orders WHERE YEAR(OrderDate) = 2024;

-- GOOD: range predicate → uses index on OrderDate
SELECT * FROM Orders
WHERE OrderDate >= '2024-01-01' AND OrderDate < '2025-01-01';

-- BAD: NOT IN with subquery → slow
SELECT * FROM Customers
WHERE CustomerID NOT IN (SELECT CustomerID FROM Orders);

-- GOOD: LEFT JOIN with NULL check, or NOT EXISTS
SELECT c.* FROM Customers c
WHERE NOT EXISTS (SELECT 1 FROM Orders o WHERE o.CustomerID = c.CustomerID);

-- BAD: N+1 queries (done in app loop)
-- GOOD: single JOIN
SELECT c.Name, o.OrderID, o.Total
FROM Customers c
LEFT JOIN Orders o ON o.CustomerID = c.CustomerID
WHERE c.CustomerID = 100;

-- 3. KEEP STATISTICS FRESH
ANALYZE Orders;                          -- PostgreSQL
ANALYZE TABLE Orders;                    -- MySQL
UPDATE STATISTICS Orders;                -- SQL Server

-- 4. LOOK FOR MISSING INDEXES
-- MySQL: suggested indexes
SELECT * FROM sys.schema_unused_indexes;
SELECT * FROM sys.schema_redundant_indexes;

-- PostgreSQL: tables with high sequential scan count
SELECT relname, seq_scan, idx_scan
FROM pg_stat_user_tables
WHERE seq_scan > idx_scan
  AND n_live_tup > 10000
ORDER BY seq_scan DESC;
Simple Example

Before tuning: SELECT * FROM Orders WHERE YEAR(OrderDate) = 2024 → full table scan, 2.5 seconds on 10M rows.

After tuning: rewrite as WHERE OrderDate BETWEEN '2024-01-01' AND '2024-12-31' and ensure an index on OrderDate → 3 milliseconds, 830× faster.

Real-Life Use Case

A dashboard page in an e-commerce app loaded in 8 seconds because it ran 47 separate queries (N+1 anti-pattern). After rewriting to fetch everything in 3 JOINed queries and adding an index on the filter column, the page loads in 90ms. Same data, same UX — just tuned.

Tuning Checklist
  • Run EXPLAIN on every query slower than 100ms.
  • Look for "Seq Scan" / "Table Scan" on big tables.
  • Check rows examined vs rows returned — huge ratio = missing index.
  • Never use SELECT * in production code.
  • Avoid functions on indexed columns in WHERE.
  • Add indexes on JOIN and ORDER BY columns.

7.5 Index Tuning and Partitioning

Definition

Index tuning is the process of choosing which indexes to create, keep, or drop. Good indexes speed up reads dramatically; useless indexes slow down writes and waste storage. Partitioning is the technique of splitting a large table into smaller physical pieces — while keeping one logical table.

Partitioning Types

1. Range Partitioning — split by a range of values

  • Most common for date-based data.
  • Example: Orders partitioned by year — 2023, 2024, 2025.
  • Queries filtering by date touch only 1 partition (partition pruning).

2. Hash Partitioning — split by hash(key) % N

  • Even distribution across N partitions.
  • Good for evenly distributing a large table with no obvious date split.
  • Example: Customers partitioned into 8 buckets by hash(CustomerID) % 8.

3. List Partitioning — split by explicit value lists

  • Each partition holds an explicit set of values.
  • Example: Customers partitioned by region — 'Asia', 'Europe', 'Americas'.

4. Composite Partitioning — combine two techniques

  • Example: range by year, then hash by customer ID within each year.

Index Tuning Best Practices

  • Index columns used in WHERE — especially high-selectivity columns.
  • Index JOIN columns — foreign keys almost always need an index.
  • Index ORDER BY columns — sorts can use the index if the leading column matches.
  • Composite indexes — order matters: put the most-filtered column first. (DeptID, Salary) helps WHERE DeptID = X AND Salary > Y, but not WHERE Salary > Y alone.
  • Covering indexes — include all columns a query needs → no table lookup.
  • Drop unused indexes — they slow INSERTs and waste storage.
  • Drop duplicate/overlapping indexes — if index on (A, B) exists, an index on (A) is redundant.
  • Monitor index usage — Postgres: pg_stat_user_indexes; MySQL: sys.schema_unused_indexes.

Diagram — Partitioning Strategies

Figure 7.5 — Range vs Hash partitioning + index tuning quick rules

Syntax — Partitioning and index tuning

SQL — Partitioning 
-- RANGE partitioning by year (MySQL 8)
CREATE TABLE Orders (
    OrderID    INT NOT NULL,
    OrderDate  DATE NOT NULL,
    Total      DECIMAL(10,2),
    PRIMARY KEY (OrderID, OrderDate)
)
PARTITION BY RANGE (YEAR(OrderDate)) (
    PARTITION p2023 VALUES LESS THAN (2024),
    PARTITION p2024 VALUES LESS THAN (2025),
    PARTITION p2025 VALUES LESS THAN (2026),
    PARTITION pmax  VALUES LESS THAN MAXVALUE
);

-- HASH partitioning (even distribution across 8 buckets)
CREATE TABLE Customers (
    CustomerID INT PRIMARY KEY,
    Name       VARCHAR(100)
)
PARTITION BY HASH (CustomerID) PARTITIONS 8;

-- LIST partitioning (explicit regions)
CREATE TABLE Sales (
    SaleID  INT PRIMARY KEY,
    Region  VARCHAR(20)
)
PARTITION BY LIST (Region) (
    PARTITION p_asia    VALUES IN ('Pakistan', 'India', 'China'),
    PARTITION p_europe  VALUES IN ('UK', 'Germany', 'France'),
    PARTITION p_america VALUES IN ('USA', 'Canada', 'Brazil')
);

-- PostgreSQL declarative partitioning
CREATE TABLE orders (
    order_id   INT,
    order_date DATE NOT NULL,
    total      DECIMAL(10,2)
) PARTITION BY RANGE (order_date);

CREATE TABLE orders_2024 PARTITION OF orders
    FOR VALUES FROM ('2024-01-01') TO ('2025-01-01');
CREATE TABLE orders_2025 PARTITION OF orders
    FOR VALUES FROM ('2025-01-01') TO ('2026-01-01');

-- See partitions
SELECT * FROM information_schema.partitions
WHERE table_name = 'Orders';
SQL — Index tuning 
-- Good indexes
CREATE INDEX idx_orders_customer ON Orders(CustomerID);   -- JOIN column
CREATE INDEX idx_orders_date     ON Orders(OrderDate);    -- range filter
CREATE INDEX idx_emp_dept_salary ON Employees(DeptID, Salary);  -- composite

-- Composite index for common query pattern
-- Query: WHERE DeptID = 10 AND Salary > 50000
-- → index (DeptID, Salary) uses both columns efficiently

-- Covering index — query answered entirely from index
CREATE INDEX idx_cover_emp ON Employees(DeptID, Name, Salary);
-- Query: SELECT Name, Salary FROM Employees WHERE DeptID = 10
-- → no table access needed!

-- ---------- Find UNUSED indexes ----------
-- MySQL
SELECT object_schema, object_name, index_name
FROM performance_schema.table_io_waits_summary_by_index_usage
WHERE index_name IS NOT NULL
  AND count_star = 0
  AND object_schema NOT IN ('mysql', 'performance_schema');

-- PostgreSQL
SELECT relname AS table, indexrelname AS index, idx_scan
FROM pg_stat_user_indexes
WHERE idx_scan = 0
ORDER BY pg_relation_size(indexrelid) DESC;

-- ---------- Find MISSING indexes ----------
-- PostgreSQL: sequential scans on big tables
SELECT relname, seq_scan, idx_scan, n_live_tup
FROM pg_stat_user_tables
WHERE seq_scan > 100
  AND n_live_tup > 10000
ORDER BY seq_scan DESC;

-- ---------- Drop unused/duplicate indexes ----------
DROP INDEX idx_old_unused ON Orders;
-- MySQL: DROP INDEX idx_name ON table;
-- PostgreSQL: DROP INDEX idx_name;
Simple Example

Partitioning: an Orders table with 100 million rows partitioned by year → "orders in 2024" query only reads the p2024 partition (25M rows), not all 100M.

Index tuning: a query filtered by department and salary works fastest with a composite index on (DeptID, Salary), not two separate indexes.

Real-Life Use Case

Banking transaction logs grow forever. Partition by month: queries "transactions this month" touch only one partition; older partitions can be compressed, moved to cheaper storage, or archived without touching live data. IoT platforms (sensor data) partition by day and use hash partitioning on device_id to spread load evenly across disks.

When to Partition
  • Table > 50 GB or > 100 million rows.
  • Queries almost always filter by a range (date, region, category).
  • You need to archive/delete old data quickly (drop a partition = instant).
  • You need to spread I/O across multiple disks.

7.6 Database Configuration Parameters

Definition

Configuration parameters are settings (in files like my.cnf for MySQL, postgresql.conf for PostgreSQL, sp_configure for SQL Server) that control how the DBMS uses CPU, memory, disk, and connections. Getting these right can be the difference between 100 QPS and 10,000 QPS — with zero schema changes.

Key Categories of Parameters

1. Memory parameters

  • Buffer pool / shared buffers — cache for data pages (biggest memory consumer).
  • Sort buffer / work_mem — memory per sort/hash operation.
  • Join buffer — memory for join operations.
  • Query cache (deprecated in MySQL 8) — cache for repeated query results.
  • Temp table size — max size for in-memory temp tables.

2. Connection parameters

  • max_connections — how many clients can connect simultaneously.
  • wait_timeout / idle_in_transaction_session_timeout — kill idle connections.
  • Connection pooling — usually handled by app or proxy (PgBouncer).

3. I/O parameters

  • innodb_io_capacity (MySQL) — how many I/O ops the SSD can handle.
  • random_page_cost / seq_page_cost (PostgreSQL) — planner estimates for disk access.
  • effective_io_concurrency — parallel I/O requests.

4. Logging & durability parameters

  • innodb_flush_log_at_trx_commit — how often to flush the log to disk (1 = safest, 2 = faster but risk).
  • wal_level, fsync (PostgreSQL) — trade-off between crash safety and speed.
  • slow_query_log — log queries slower than long_query_time.

5. Parallelism parameters

  • max_parallel_workers (PostgreSQL).
  • max_worker_processes.

# --- PARALLELISM ---

Simple Example

A 32 GB RAM server running MySQL: innodb_buffer_pool_size = 24G (75% of RAM). With this, 99%+ of pages stay in memory, so most queries never touch disk — massive speedup. If you set it to 2 GB, most queries would hit disk → 100× slower.

Real-Life Use Case

A startup deploys MySQL with default config (buffer pool = 128 MB). Their app gets slow as data grows. The DBA increases innodb_buffer_pool_size to 8 GB, adds 4 buffer pool instances, enables slow query log. Result: average query time drops from 400ms to 12ms — with zero schema changes. This is often the single biggest performance win available.

Don't Overallocate Memory

Setting innodb_buffer_pool_size = 100% of RAM causes the OS to swap, which is catastrophically slow. Leave room for:
• OS operations (typically 1–4 GB)
• Per-connection memory (sort buffers × max_connections)
• File system cache (indirect but useful for temp files)

Configuration Tuning Order
  1. Set buffer pool / shared buffers (~70% RAM) — biggest impact.
  2. Set max_connections realistically — 1000 idle connections is worse than 100 busy ones.
  3. Enable slow query log — find the real problem queries.
  4. Tune work_mem / sort_buffer_size only after query analysis.
  5. Don't touch durability knobs (fsync, synchronous_commit) unless you fully understand them.

Syntax — Monitoring queries

SQL — Key metrics queries 
-- ---------- MySQL ----------

-- Buffer pool hit ratio (target > 99%)
SELECT
    ROUND(100 * (1 - (variable_value /
        (SELECT variable_value FROM performance_schema.global_status
         WHERE variable_name = 'Innodb_buffer_pool_read_requests'))), 2) AS hit_ratio_pct
FROM performance_schema.global_status
WHERE variable_name = 'Innodb_buffer_pool_reads';

-- Or simpler:
SHOW GLOBAL STATUS LIKE 'Innodb_buffer_pool_read%';

-- Active connections
SHOW STATUS LIKE 'Threads_connected';
SHOW VARIABLES LIKE 'max_connections';

-- Slow queries
SHOW GLOBAL STATUS LIKE 'Slow_queries';

-- Deadlocks per hour
SHOW ENGINE INNODB STATUS\G
-- Look for "LATEST DETECTED DEADLOCK"

-- Currently running queries
SELECT id, user, host, db, command, time, state, info
FROM information_schema.processlist
WHERE command <> 'Sleep'
ORDER BY time DESC;

-- Queries running longer than 60 seconds
SELECT id, user, time, info
FROM information_schema.processlist
WHERE time > 60 AND info IS NOT NULL;

-- Tables with missing indexes (high rows_read vs rows_returned)
SELECT * FROM sys.schema_tables_with_full_table_scans;

-- ---------- PostgreSQL ----------

-- Connection count / max
SELECT count(*) AS active, current_setting('max_connections')::int AS max_conn
FROM pg_stat_activity
WHERE state = 'active';

-- Buffer hit ratio
SELECT
    sum(heap_blks_hit) * 100.0 /
    nullif(sum(heap_blks_hit) + sum(heap_blks_read), 0) AS buffer_hit_ratio
FROM pg_statio_user_tables;

-- Long-running queries
SELECT pid, now() - query_start AS duration, query, state
FROM pg_stat_activity
WHERE state = 'active'
  AND now() - query_start > interval '1 minute'
ORDER BY duration DESC;

-- Lock waits
SELECT pid, wait_event_type, wait_event, query
FROM pg_stat_activity
WHERE wait_event_type = 'Lock';

-- Replication lag (on replica)
SELECT now() - pg_last_xact_replay_timestamp() AS replication_lag;

-- Table bloat / dead rows (autovacuum health)
SELECT relname, n_live_tup, n_dead_tup,
       round(100.0 * n_dead_tup / nullif(n_live_tup + n_dead_tup, 0), 2) AS dead_pct
FROM pg_stat_user_tables
WHERE n_dead_tup > 1000
ORDER BY n_dead_tup DESC;

Simple Example

Problem: users report the app is "slow" — no specific error.

Step 1 (monitor): check dashboard — QPS steady at 8K, but P95 latency up from 40ms → 800ms.

Step 2 (drill down): slow query log shows SELECT * FROM Orders WHERE CustomerID = ? taking 900ms (was 5ms).

Step 3 (analyze): EXPLAIN shows a full table scan — the index idx_orders_customer was accidentally dropped in yesterday's migration!

Step 4 (fix): re-create the index → latency back to 40ms. Monitoring caught it in minutes, not hours.

Real-Life Use Case

Large SaaS platforms run continuous monitoring with Prometheus + Grafana. They alert on P99 latency, buffer pool hit ratio, and replication lag. When a deployment accidentally introduces an N+1 query, the QPS metric spikes, an alert fires, the on-call engineer rolls back — all within minutes. Without monitoring, users would notice before the team does.

Monitoring is not "checking once a day"

Modern monitoring is continuous (metrics collected every 10–60 seconds), automated (alerts fire without human intervention), and comprehensive (database + application + infrastructure). Good monitoring reduces MTTR (Mean Time To Recover) from hours to minutes.
