3.1 Introduction to Query Languages

Definition

A query language is a specialized computer language used to communicate with a database — to retrieve, insert, update, delete, and manage data. Unlike general-purpose languages (Java, Python), a query language is designed to describe what data you want rather than how to get it. This is called being declarative.

Types of Query Languages

  • Declarative (Non-procedural) — describe what — e.g., SQL, QBE.
  • Procedural — describe how — e.g., Relational Algebra (used internally by DBMS).
  • Graph query languages — for graph databases — Cypher, Gremlin, SPARQL.
  • NoSQL query languages — MongoDB Query Language (MQL), Cassandra Query Language (CQL).
  • XQuery / XPath — for XML data.

Why Query Languages Matter

  • Standard, portable way to interact with databases.
  • Hides low-level storage details from the user.
  • Powers the DBMS query optimizer to find efficient execution paths.
  • Enables non-programmers to query data directly.

Diagram — Layers of Interaction

Figure 3.1 — Users write queries in a query language; DBMS turns them into results
Simple Example

Declarative (SQL): SELECT Name FROM Students WHERE Age > 20;

Procedural (Relational Algebra): π_Name (σ_Age>20 (Students))

Both do the same thing — SQL just says what, RA says how the steps work.

Real-Life Use Case

A business analyst types a SQL query in Looker to pull sales for the last quarter. The same data is also exposed to a Python application via an API. Both use the same declarative query language (SQL) — the DBMS optimizes each query independently.

3.2 Structured Query Language (SQL) — Overview

Definition

SQL (Structured Query Language) is the standard declarative language for interacting with relational databases. It was developed at IBM in the 1970s (originally SEQUEL) and standardized by ANSI in 1986. Almost every relational database system (MySQL, Oracle, PostgreSQL, SQL Server) supports SQL.

The Five SQL Sublanguages

CategoryPurposeKey Commands
DDL — Data DefinitionDefine and modify structureCREATE, ALTER, DROP, TRUNCATE
DML — Data ManipulationChange dataINSERT, UPDATE, DELETE
DQL — Data QueryRetrieve dataSELECT
DCL — Data ControlControl permissionsGRANT, REVOKE
TCL — Transaction ControlManage transactionsCOMMIT, ROLLBACK, SAVEPOINT

Diagram — SQL Family Tree

Figure 3.2 — SQL's five sublanguages at a glance

Syntax — A taste of each sublanguage

SQL — Overview 
-- DDL: define structure
CREATE TABLE Students (StudentID INT PRIMARY KEY, Name VARCHAR(100));

-- DML: manipulate data
INSERT INTO Students VALUES (1, 'Ali');

-- DQL: query data
SELECT * FROM Students WHERE Name = 'Ali';

-- DCL: control permissions
GRANT SELECT ON Students TO 'ali'@'localhost';

-- TCL: control transactions
COMMIT;
Simple Example

Building an app? You use DDL once to create tables, DML every time a user places an order, DQL to show their order history, DCL to give access to certain staff, and TCL to ensure their payment is committed atomically.

Real-Life Use Case

Every major application — Instagram, Amazon, banking apps — runs SQL in some form. Amazon Aurora, Google Cloud SQL, and Azure SQL are all based on SQL. The language is so universal that a developer who knows SQL can move between MySQL, Oracle, and PostgreSQL with minimal retraining.

3.3 DDL (Data Definition Language) — CREATE, ALTER, DROP

Definition

DDL (Data Definition Language) is the subset of SQL used to define and manage the structure of database objects — tables, views, indexes, schemas. DDL statements change the schema, not the data inside it.

Core DDL Commands

  • CREATE — make a new table, view, index, or schema.
  • ALTER — modify an existing object (add/drop column, change type, add constraint).
  • DROP — delete an object entirely (table + data + structure).
  • TRUNCATE — delete all rows but keep the table structure.
  • RENAME — rename a table or column.
  • COMMENT — add descriptive comments to objects.

Diagram — CREATE → ALTER → DROP lifecycle

Figure 3.3 — Table lifecycle: create → alter → truncate → drop

Syntax — All three commands in action

SQL — DDL 
-- CREATE: build a new table
CREATE TABLE Employees (
    EmpID     INT PRIMARY KEY AUTO_INCREMENT,
    Name      VARCHAR(100) NOT NULL,
    Salary    DECIMAL(10,2),
    DeptID    INT,
    HireDate  DATE DEFAULT CURRENT_DATE
);

-- ALTER: add a new column
ALTER TABLE Employees
    ADD Email VARCHAR(150) UNIQUE;

-- ALTER: change a column's data type
ALTER TABLE Employees
    MODIFY Salary DECIMAL(12,2) NOT NULL;

-- ALTER: add a foreign key constraint
ALTER TABLE Employees
    ADD CONSTRAINT fk_dept
        FOREIGN KEY (DeptID) REFERENCES Departments(DeptID);

-- TRUNCATE: empty the table but keep structure
TRUNCATE TABLE Employees;

-- DROP: delete the table completely
DROP TABLE Employees;
Simple Example

CREATE — you build a new Orders table.

ALTER — you realize you forgot a status column; you add it.

DROP — the business closes; you delete the table completely.

Real-Life Use Case

In an e-commerce startup, DDL is used at setup: create Customers, Products, Orders tables. Six months later, the marketing team wants to track coupons, so a new CouponCode column is added via ALTER. When a legacy table becomes obsolete, it's dropped.

Warning: DROP is irreversible

DROP TABLE deletes structure and data — no undo. TRUNCATE deletes all rows but keeps the table. Always back up before running DDL in production.

3.4 DML (Data Manipulation Language) — INSERT, UPDATE, DELETE

Definition

DML (Data Manipulation Language) is the subset of SQL used to manipulate the data inside tables — adding new rows, changing existing rows, and removing rows. Unlike DDL, DML changes the data but not the structure.

Core DML Commands

  • INSERT — add new rows.
  • UPDATE — modify existing rows.
  • DELETE — remove rows.
  • MERGE / UPSERT — insert if new, update if existing (in some DBMS).

Diagram — DML Operations

Figure 3.4 — INSERT adds rows, UPDATE modifies rows, DELETE removes rows

Syntax — All three commands in action

SQL — DML 
-- INSERT: add one row
INSERT INTO Employees (EmpID, Name, Salary, DeptID)
VALUES (1, 'Ali', 50000, 10);

-- INSERT: add multiple rows at once (faster than one-by-one)
INSERT INTO Employees (EmpID, Name, Salary, DeptID)
VALUES (2, 'Sara', 55000, 10),
       (3, 'Bilal', 70000, 20),
       (4, 'Hina', 68000, 20);

-- INSERT from another table (bulk copy)
INSERT INTO Employees_Archive (EmpID, Name, Salary)
SELECT EmpID, Name, Salary FROM Employees WHERE HireDate < '2023-01-01';

-- UPDATE: modify existing rows
UPDATE Employees
SET Salary = Salary * 1.10
WHERE DeptID = 10;

-- UPDATE with a join (MySQL syntax)
UPDATE Employees e
JOIN Departments d ON e.DeptID = d.DeptID
SET e.Salary = e.Salary * 1.05
WHERE d.DeptName = 'Sales';

-- DELETE: remove specific rows
DELETE FROM Employees
WHERE EmpID = 4;

-- DELETE all rows (but table structure remains — DML, not DDL)
DELETE FROM Employees;
Simple Example

INSERT: a new user signs up — you INSERT INTO Users VALUES (101, 'Ali', 'ali@example.com').

UPDATE: they change their email — you UPDATE Users SET Email = 'new@example.com' WHERE UserID = 101.

DELETE: they close their account — you DELETE FROM Users WHERE UserID = 101.

Real-Life Use Case

Every e-commerce order triggers DML: new row in Orders, several in OrderItems, an UPDATE to reduce stock in Products. When a product is discontinued, it's DELETEd or marked inactive. All of this is standard DML — often wrapped in a transaction (see Topic 3.7) to ensure consistency.

Warning: Always use WHERE with UPDATE/DELETE

UPDATE Employees SET Salary = 10000; updates every row! Always include a WHERE clause unless you truly intend to change every record. Run a SELECT with the same WHERE first to verify.

3.5 DQL (Data Query Language) — SELECT, JOINs, Subqueries

Definition

DQL (Data Query Language) is the subset of SQL used to retrieve data. Its only command is SELECT, but it's the most powerful and most-used SQL statement. You can filter, sort, aggregate, join multiple tables, nest subqueries, and more.

Anatomy of a SELECT

  1. SELECT — which columns to return
  2. FROM — which table(s)
  3. WHERE — which rows to include
  4. GROUP BY — group rows for aggregation
  5. HAVING — filter groups
  6. ORDER BY — sort the result
  7. LIMIT / OFFSET — restrict rows returned

Diagram — Types of JOINs

Figure 3.5 — JOIN types and subqueries (a nested SELECT inside another query)

Syntax — SELECT, JOIN, and Subquery examples

SQL — DQL Basics 
-- 1. Basic SELECT with filter and sort
SELECT Name, Salary
FROM Employees
WHERE Salary > 50000
ORDER BY Salary DESC
LIMIT 10;

-- 2. Aggregate with GROUP BY + HAVING
SELECT DeptID, COUNT(*) AS EmployeeCount, AVG(Salary) AS AvgSalary
FROM Employees
GROUP BY DeptID
HAVING AVG(Salary) > 55000;

-- 3. INNER JOIN — only rows that match in both tables
SELECT e.Name, d.DeptName
FROM Employees e
INNER JOIN Departments d ON e.DeptID = d.DeptID;

-- 4. LEFT JOIN — all employees, even if they have no department
SELECT e.Name, d.DeptName
FROM Employees e
LEFT JOIN Departments d ON e.DeptID = d.DeptID;

-- 5. Subquery — employees earning above the company average
SELECT Name, Salary
FROM Employees
WHERE Salary > (SELECT AVG(Salary) FROM Employees);

-- 6. Subquery with IN — employees in departments with >5 people
SELECT Name
FROM Employees
WHERE DeptID IN (
    SELECT DeptID FROM Employees
    GROUP BY DeptID
    HAVING COUNT(*) > 5
);

-- 7. Correlated subquery — employees earning above their own dept average
SELECT e1.Name, e1.Salary, e1.DeptID
FROM Employees e1
WHERE e1.Salary > (
    SELECT AVG(e2.Salary)
    FROM Employees e2
    WHERE e2.DeptID = e1.DeptID
);
Simple Example

SELECT + WHERE: "Show me employees with salary over 50k."

JOIN: "Show each employee along with their department's name."

Subquery: "Show employees who earn more than the company average."

Real-Life Use Case

An e-commerce dashboard uses DQL constantly: JOIN Orders with Customers to show "who bought what," uses a subquery to find products never ordered, aggregates SUM(total) per month, and sorts by revenue. This is the daily work of every analyst and backend developer.

3.6 DCL (Data Control Language) — GRANT, REVOKE

Definition

DCL (Data Control Language) is the subset of SQL used to control access to the database. It manages who can do what — which users can read, insert, update, or delete data, and which objects they can access.

Core DCL Commands

  • GRANT — give a privilege to a user or role.
  • REVOKE — take away a privilege.
  • DENY — explicitly deny a privilege (SQL Server).

Common Privileges

  • SELECT — read data
  • INSERT — add rows
  • UPDATE — modify rows
  • DELETE — remove rows
  • CREATE / DROP / ALTER — DDL privileges
  • EXECUTE — run stored procedures
  • ALL PRIVILEGES — everything

Diagram — GRANT / REVOKE flow

Figure 3.6 — GRANT gives privileges, REVOKE takes them away

Syntax — GRANT / REVOKE examples

SQL — DCL 
-- 1. Create a user
CREATE USER 'ali'@'localhost' IDENTIFIED BY 'SecurePass123';

-- 2. GRANT: give SELECT and INSERT on Students table only
GRANT SELECT, INSERT ON SchoolDB.Students TO 'ali'@'localhost';

-- 3. GRANT multiple privileges on all tables in a database
GRANT SELECT, UPDATE, DELETE ON SchoolDB.* TO 'ali'@'localhost';

-- 4. GRANT with the option to pass it on (grant option)
GRANT SELECT ON SchoolDB.Students TO 'ali'@'localhost'
    WITH GRANT OPTION;

-- 5. GRANT a role to a user (cleaner than per-object grants)
CREATE ROLE read_only;
GRANT SELECT ON SchoolDB.* TO read_only;
GRANT read_only TO 'sara'@'localhost';

-- 6. REVOKE: take away INSERT — keep SELECT
REVOKE INSERT ON SchoolDB.Students FROM 'ali'@'localhost';

-- 7. REVOKE all privileges (careful!)
REVOKE ALL PRIVILEGES, GRANT OPTION FROM 'ali'@'localhost';

-- 8. See what a user has
SHOW GRANTS FOR 'ali'@'localhost';
Simple Example

GRANT: the marketing intern needs to see sales data but not change it — you GRANT SELECT ON Sales TO intern.

REVOKE: the intern's access is no longer needed — you REVOKE SELECT ON Sales FROM intern.

Real-Life Use Case

A hospital database has three roles: doctors (read all patient data), nurses (read + write vitals but not billing), billing staff (read + write billing but no clinical data). DCL creates those roles and grants exactly the right privileges to each — enforcing least privilege and HIPAA compliance.

Principle of Least Privilege

Always grant the minimum privileges a user needs. Never grant ALL PRIVILEGES to regular app users — a compromised account with ALL can delete or steal the entire database.

3.7 TCL (Transaction Control Language) — COMMIT, ROLLBACK, SAVEPOINT

Definition

TCL (Transaction Control Language) is the subset of SQL used to manage transactions — a group of DML statements treated as one unit. Either all of them succeed, or none of them take effect. This ensures the ACID properties (Atomicity, Consistency, Isolation, Durability).

Core TCL Commands

  • COMMIT — permanently save all changes in the transaction.
  • ROLLBACK — undo all changes since the transaction began (or since last SAVEPOINT).
  • SAVEPOINT — create a named point you can roll back to (partial rollback).
  • RELEASE SAVEPOINT — delete a savepoint (free up resources).
  • SET TRANSACTION — set isolation level, read-only, etc.

Diagram — Transaction flow with SAVEPOINT

Figure 3.7 — Transaction timeline with SAVEPOINTs, ROLLBACK, and COMMIT

Syntax — Full transaction example

SQL — TCL (bank transfer) 
-- Classic bank transfer: deduct from A, add to B — both or neither
START TRANSACTION;   -- or: BEGIN;

-- Step 1: deduct 500 from Alice's account
UPDATE Accounts SET Balance = Balance - 500 WHERE AccountID = 1;

-- Create a savepoint after the first step
SAVEPOINT after_deduct;

-- Step 2: add 500 to Bob's account
UPDATE Accounts SET Balance = Balance + 500 WHERE AccountID = 2;

-- If something goes wrong (e.g., Bob's account closed), undo step 2:
ROLLBACK TO after_deduct;

-- But if step 2 also works, save everything:
COMMIT;

-- ---------- Example with ROLLBACK to a savepoint ----------
START TRANSACTION;

INSERT INTO Orders (OrderID, CustomerID, Total) VALUES (1001, 10, 250.00);
SAVEPOINT s1;

INSERT INTO OrderItems VALUES (1001, 'P101', 2);
SAVEPOINT s2;

INSERT INTO OrderItems VALUES (1001, 'P999', 1);   -- bad product ID!

-- Oops — roll back only the last insert, keep the rest
ROLLBACK TO s2;

-- Now fix and try again
INSERT INTO OrderItems VALUES (1001, 'P102', 1);

COMMIT;

-- ---------- Full rollback example ----------
START TRANSACTION;
DELETE FROM Products WHERE Price > 10000;
-- Realize this was a mistake:
ROLLBACK;   -- everything since BEGIN is undone
Simple Example

A bank transfer from Alice to Bob involves two UPDATEs. If the second one fails (say, Bob's account is locked), the whole transfer must be cancelled — otherwise Alice loses 500 and Bob gains nothing. TCL makes this atomic: START TRANSACTION → both UPDATEs → COMMIT on success, or ROLLBACK on any failure.

Real-Life Use Case

Every ATM withdrawal is a transaction: dispense cash and update the balance — both must succeed. If the cash dispenser jams after the balance is updated, ROLLBACK reverses the deduction. Similarly, flight bookings use TCL to reserve seats across multiple systems (inventory, payment, ticketing) — either all succeed or all fail.

Implicit vs Explicit Transactions

By default, most DBMS use autocommit — every statement is its own transaction. Wrap multiple statements in START TRANSACTION … COMMIT when they must succeed or fail together.

3.8 Query Specifications and Optimization Basics

Definition

Query optimization is the process by which the DBMS finds the most efficient way to execute a query. A single SQL query can often be executed in many different ways (different join orders, index usage, etc.), and the optimizer's job is to choose the cheapest plan. Query specification refers to how well the query is written — clear, precise SQL helps the optimizer do its job.

Why Optimization Matters

  • A poorly tuned query can take minutes; the same query optimized can take milliseconds.
  • Reduces load on the database server (CPU, memory, disk I/O).
  • Improves user experience — fast apps need fast queries.
  • Scales better as data grows.

How the Optimizer Works

  1. Parse — check syntax.
  2. Validate — check tables/columns exist, permissions.
  3. Rewrite — apply algebraic rules (e.g., push WHERE down).
  4. Plan — consider multiple execution plans.
  5. Cost — estimate cost of each plan using statistics.
  6. Choose — pick the lowest-cost plan.
  7. Execute — run the chosen plan.

Diagram — Query Optimization Pipeline

Figure 3.8 — How a query flows through the optimizer

Syntax — Analyzing and improving queries

SQL — EXPLAIN + tuning 
-- 1. See the execution plan (MySQL)
EXPLAIN SELECT * FROM Employees WHERE Name = 'Ali';

-- PostgreSQL version
EXPLAIN ANALYZE SELECT * FROM Employees WHERE Name = 'Ali';

-- 2. SLOW query — no index on Name
SELECT * FROM Employees WHERE Name = 'Ali';      -- full table scan!

-- 3. Add an index — now the query uses an index scan
CREATE INDEX idx_employees_name ON Employees(Name);

-- 4. Avoid SELECT * — fetch only what you need
-- BAD (reads extra columns, more I/O)
SELECT * FROM Employees WHERE DeptID = 10;

-- GOOD (reads only needed columns)
SELECT Name, Salary FROM Employees WHERE DeptID = 10;

-- 5. Filter early — push WHERE into subqueries
-- BAD (aggregates everything then filters)
SELECT * FROM (
  SELECT DeptID, AVG(Salary) AS AvgSal
  FROM Employees
  GROUP BY DeptID
) AS sub
WHERE AvgSal > 60000;

-- GOOD (filters before aggregation)
SELECT DeptID, AVG(Salary) AS AvgSal
FROM Employees
GROUP BY DeptID
HAVING AVG(Salary) > 60000;

-- 6. Use EXISTS instead of IN when possible (better for large sets)
SELECT * FROM Employees e
WHERE EXISTS (
    SELECT 1 FROM Departments d
    WHERE d.DeptID = e.DeptID AND d.Budget > 1000000
);
Simple Example

Before: SELECT * FROM Orders WHERE CustomerID = 101; without an index → scans 1M rows in 2 seconds.

After: CREATE INDEX idx_orders_cust ON Orders(CustomerID); → same query in 5ms.

Real-Life Use Case

An e-commerce site's "order history" page was taking 8 seconds to load. Running EXPLAIN revealed a full table scan on 50 million orders. Adding a composite index on (CustomerID, OrderDate) and rewriting the query to avoid SELECT * reduced load time to 40ms.

Golden Rules
  • Always filter with WHERE before sorting/aggregating.
  • Avoid SELECT * — fetch only what you need.
  • Use indexes on columns in WHERE, JOIN, and ORDER BY.
  • Run EXPLAIN before deploying any slow query.
  • Keep statistics up-to-date (let the DBMS auto-analyze).

3.9 Stored Procedures, Functions, and Triggers

Definition

These are server-side programs stored inside the database. Instead of sending many SQL statements from the application each time, you save the logic once in the DBMS and call it with a single command.

  • Stored Procedure — a named block of SQL that performs an action. Can accept parameters, return multiple result sets, and contain transaction logic. Called with CALL.
  • Function — a routine that returns a single value (scalar) or a table. Can be used inside SELECT statements, WHERE clauses, etc.
  • Trigger — a block of SQL that runs automatically in response to a DML event (INSERT, UPDATE, DELETE) on a specific table. Cannot be called manually.

Comparison

AspectStored ProcedureFunctionTrigger
Returns0+ values / result setsExactly 1 value (or table)Nothing
Called byUser or app (CALL)Inside SQL expressionsDBMS event (INSERT/UPDATE/DELETE)
Can modify data?YesUsually no (read-only)Yes (BEFORE/AFTER)
Transaction controlYesNoNo
Common useBusiness logic, batch jobsComputed columns, validationsAuditing, enforcing rules

Diagram — Where each lives

Figure 3.9 — Procedures/functions are called; triggers fire automatically on DML

Syntax — All three examples (MySQL)

SQL — Stored Procedure 
DELIMITER $

CREATE PROCEDURE GiveRaise(IN p_dept_id INT, IN p_percent DECIMAL(5,2))
BEGIN
    UPDATE Employees
    SET Salary = Salary * (1 + p_percent / 100)
    WHERE DeptID = p_dept_id;

    SELECT CONCAT('Raise applied to ', ROW_COUNT(), ' employees') AS Status;
END$

DELIMITER ;

-- Call it
CALL GiveRaise(10, 10);   -- 10% raise to all in dept 10
SQL — Function 
DELIMITER $

CREATE FUNCTION CalculateBonus(p_salary DECIMAL(10,2))
RETURNS DECIMAL(10,2)
DETERMINISTIC
BEGIN
    DECLARE bonus DECIMAL(10,2);

    IF p_salary > 80000 THEN
        SET bonus = p_salary * 0.15;
    ELSEIF p_salary > 50000 THEN
        SET bonus = p_salary * 0.10;
    ELSE
        SET bonus = p_salary * 0.05;
    END IF;

    RETURN bonus;
END$

DELIMITER ;

-- Use it in a SELECT (like a built-in function)
SELECT Name, Salary, CalculateBonus(Salary) AS Bonus
FROM Employees;
SQL — Trigger 
-- First, create an audit table
CREATE TABLE SalaryAudit (
    AuditID    INT AUTO_INCREMENT PRIMARY KEY,
    EmpID      INT,
    OldSalary  DECIMAL(10,2),
    NewSalary  DECIMAL(10,2),
    ChangedAt  TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    ChangedBy  VARCHAR(100)
);

DELIMITER $

-- AFTER UPDATE trigger: automatically log any salary change
CREATE TRIGGER trg_salary_audit
AFTER UPDATE ON Employees
FOR EACH ROW
BEGIN
    IF OLD.Salary <> NEW.Salary THEN
        INSERT INTO SalaryAudit (EmpID, OldSalary, NewSalary, ChangedBy)
        VALUES (OLD.EmpID, OLD.Salary, NEW.Salary, USER());
    END IF;
END$

DELIMITER ;

-- Now every salary change is logged — automatically!
UPDATE Employees SET Salary = 60000 WHERE EmpID = 1;
-- Check the audit table:
SELECT * FROM SalaryAudit;
Simple Example

Stored Procedure: "Give a 10% raise to everyone in department 10" — run CALL GiveRaise(10, 10).

Function: "Calculate bonus based on salary" — used inside a SELECT: SELECT Name, CalculateBonus(Salary) FROM Employees.

Trigger: "Log every salary change automatically" — the trigger fires when anyone runs UPDATE on Employees, no matter who.

Real-Life Use Case

Banking: a stored procedure TransferFunds(from_acct, to_acct, amount) wraps the whole transaction logic — used by both mobile app and web app, so business rules live in one place. A trigger automatically logs every balance change to an Audit table for compliance. A function CalculateInterest(principal, years) is used in reports and dashboards.

Best Practices
  • Keep procedures/functions short and focused.
  • Use triggers sparingly — they can cause hard-to-debug side effects.
  • Document all triggers (a trigger firing on every update can silently slow down bulk operations).
  • Version-control your stored routines like any other code.
