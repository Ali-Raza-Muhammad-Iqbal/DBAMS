5.1 Principles of Database Management Systems

Definition

The principles of DBMS are the core guarantees that a database management system must provide so that applications can trust the data. These principles ensure that data remains correct, safe, consistent, and available even when many users and failures happen simultaneously.

Core Principles

  • Data Integrity — data is always valid and consistent with constraints (PK, FK, CHECK).
  • Data Security — only authorized users can access or modify data (GRANT/REVOKE, roles, encryption).
  • Data Independence — change the physical storage without breaking applications (three-schema architecture).
  • Concurrency — many users can work simultaneously without corrupting each other's data.
  • Recovery — after a crash, the DBMS restores the data to a consistent state.
  • Atomicity of operations — multi-step operations either fully succeed or fully fail (transactions).
  • Durability — once a transaction is committed, it survives power loss.
  • Efficiency — queries and updates run fast (indexes, optimizer, buffer pool).

Diagram — DBMS Principles Pillars

Figure 5.1 — Six pillars of DBMS principles around a central core

Syntax — Principles enforced by the DBMS

SQL — Principles in action 
-- Integrity: enforce valid data
CREATE TABLE Accounts (
    AccountID INT PRIMARY KEY,
    Balance   DECIMAL(10,2) CHECK (Balance >= 0)  -- never negative
);

-- Security: only authorized users
GRANT SELECT ON Accounts TO 'auditor'@'localhost';
REVOKE INSERT ON Accounts FROM 'auditor'@'localhost';

-- Concurrency: two transfers don't interfere
START TRANSACTION;
UPDATE Accounts SET Balance = Balance - 100 WHERE AccountID = 1;
UPDATE Accounts SET Balance = Balance + 100 WHERE AccountID = 2;
COMMIT;

-- Recovery: after a crash, the DBMS uses the redo/undo log
-- to restore the last consistent state (no code needed — automatic).
Simple Example

When Alice transfers $100 to Bob, the DBMS guarantees: (1) her balance drops AND Bob's rises (atomicity); (2) both balances stay non-negative (integrity); (3) no other user sees a partial state (concurrency); (4) after power loss, both changes are either both present or both absent (durability).

Real-Life Use Case

Every banking system relies on these principles. When 10,000 customers make ATM withdrawals simultaneously, the DBMS ensures no one's balance becomes inconsistent. When a server crashes mid-transaction, the recovery system replays the log to restore the correct balances — customers never see or lose money.

5.2 ACID Properties (Atomicity, Consistency, Isolation, Durability)

Definition

ACID is a set of four properties that guarantee database transactions are processed reliably. Every serious relational DBMS is ACID-compliant. Together they ensure that even with concurrent users and system crashes, the database remains correct.

The Four ACID Properties

1. Atomicity ("All or Nothing")

  • A transaction is treated as a single unit — either all its operations succeed, or none do.
  • If the transaction fails halfway, the DBMS rolls back any changes already made.

2. Consistency ("Valid to Valid")

  • A transaction takes the database from one valid state to another valid state.
  • All constraints (PK, FK, CHECK) must hold before and after.
  • If a transaction would violate a constraint, it's aborted.

3. Isolation ("No Interference")

  • Concurrent transactions don't see each other's uncommitted changes.
  • Each transaction feels like it's running alone.
  • Implemented via locking or multiversioning (MVCC).

4. Durability ("Survives Crashes")

  • Once a transaction is COMMITted, its changes are permanent — even if the system crashes immediately after.
  • Implemented via write-ahead logging (WAL) and fsync.

Diagram — The ACID Quadrant

Figure 5.2 — The four ACID guarantees of a transaction

Syntax — ACID in SQL

SQL — ACID transfer 
-- Classic bank transfer: 100 from A to B

-- ATOMICITY: use a transaction so both UPDATEs succeed or both fail
START TRANSACTION;

-- CONSISTENCY: constraint ensures balances never go negative
UPDATE Accounts SET Balance = Balance - 100 WHERE AccountID = 1;
UPDATE Accounts SET Balance = Balance + 100 WHERE AccountID = 2;

-- ISOLATION: other sessions won't see the new balances until COMMIT
COMMIT;   -- DURABILITY: flushed to disk + WAL → survives crash

-- If anything failed, ROLLBACK would undo BOTH updates

-- ---------- Level of isolation can be tuned ----------
SET TRANSACTION ISOLATION LEVEL READ COMMITTED;
-- Options: READ UNCOMMITTED, READ COMMITTED, REPEATABLE READ, SERIALIZABLE
-- (higher = more isolation, less concurrency)
Simple Example

Atomicity: if the second UPDATE fails, the first is undone — Alice doesn't lose $100.

Consistency: CHECK constraint (Balance >= 0) prevents overdrafts.

Isolation: another customer querying at the same time sees either the before-state or after-state, never mid-state.

Durability: once COMMIT returns, the change survives even if the server's power dies immediately.

Real-Life Use Case

Every payment — credit card charge, PayPal, Stripe, UPI — relies on ACID. When you tap "Buy Now," a transaction debits your account, credits the seller, and records the order. If any step fails (fraud check, inventory, payment gateway), the entire transaction is rolled back and no money moves.

Isolation Levels
  • READ UNCOMMITTED — fastest, allows dirty reads (bad for money).
  • READ COMMITTED — default in most DBMSs, avoids dirty reads.
  • REPEATABLE READ — stable snapshots, avoids non-repeatable reads.
  • SERIALIZABLE — strictest, transactions appear fully serial.

5.3 Transaction Processing — Concepts and States

Definition

A transaction is a logical unit of database work — a sequence of operations (read, write) that must be executed as a single, indivisible unit. Transaction processing is the DBMS's management of transactions from start to finish, ensuring ACID properties even when many run concurrently and crashes occur.

Transaction States

A transaction goes through up to five states during its lifetime:

  1. Active — the transaction is executing; reads/writes are happening.
  2. Partially Committed — the final operation has executed, but changes haven't been flushed to disk yet.
  3. Committed — all changes are permanently written to disk. Cannot be rolled back.
  4. Failed — an error occurred or the transaction was aborted; changes must be undone.
  5. Aborted (Rolled Back) — the DBMS has undone all changes; the transaction is terminated.

Diagram — Transaction State Machine

Figure 5.3 — Transaction state machine: Active → Partially Committed → Committed (or Failed → Aborted)

Syntax — Observing transaction states

SQL — Transaction lifecycle 
-- ACTIVE: transaction begins, statements start executing
START TRANSACTION;
UPDATE Accounts SET Balance = Balance - 100 WHERE AccountID = 1;
-- Still ACTIVE until last statement runs

UPDATE Accounts SET Balance = Balance + 100 WHERE AccountID = 2;
-- Now PARTIALLY COMMITTED — last op done, not yet durable

COMMIT;
-- Now COMMITTED — changes flushed to disk, WAL entry written

-- ---------- Failure path ----------
START TRANSACTION;
UPDATE Accounts SET Balance = Balance - 100 WHERE AccountID = 1;
-- Error occurs (e.g., constraint violation) → FAILED state
ROLLBACK;
-- Now ABORTED — all changes undone

-- ---------- See current transactions ----------
-- MySQL
SHOW PROCESSLIST;

-- PostgreSQL
SELECT pid, state, query FROM pg_stat_activity WHERE state <> 'idle';
Simple Example

Ordering pizza online: Active = adding items to cart. Partially Committed = payment authorized. Committed = order confirmed, restaurant notified. Failed = card declined. Aborted = order cancelled, no charge made.

Real-Life Use Case

A stock trading platform executes a buy order as a transaction: Active when the order enters the matching engine, Partially Committed when the trade is matched, Committed when settlement is confirmed. If the network drops mid-trade, the state machine ensures the trade is either fully executed or fully undone — no half-completed trades.

5.4 Transaction Management and Schedules

Definition

Transaction management is the DBMS subsystem that controls how multiple transactions execute relative to each other. A schedule is the chronological order in which the operations (read, write) of multiple transactions are executed. The scheduler's job is to pick schedules that keep the database consistent and preserve ACID.

Types of Schedules

1. Serial Schedule

  • Transactions run one after another — no overlap.
  • Always correct, but slow (no concurrency).

2. Concurrent Schedule

  • Transactions interleave — operations from T1 and T2 overlap.
  • Much faster but can produce anomalies if not controlled.

3. Serializability (Special Case)

  • A concurrent schedule is serializable if its outcome is the same as some serial schedule. (More in Topic 5.5.)

4. Non-Serializable Schedule

  • Concurrent schedule that does not match any serial order — can violate correctness.

Notation for Schedules

  • R_i(X) — transaction Ti reads item X.
  • W_i(X) — transaction Ti writes item X.
  • C_i — Ti commits.
  • A_i — Ti aborts.

Diagram — Serial vs Concurrent Schedules

Figure 5.4 — Serial (one at a time) vs concurrent (interleaved) schedules

Syntax — Schedule notation in practice

SQL — Concurrent schedule 
-- A concurrent schedule looks like this (in notation):
-- S = R1(X), R2(X), W1(X), W2(X), C1, C2
-- (T1 reads X, T2 reads X, T1 writes X, T2 writes X, ...)

-- In real SQL, two sessions overlap like this:
-- Session 1 (T1)                    Session 2 (T2)
-- ----------------                  ----------------
START TRANSACTION;                     START TRANSACTION;
SELECT Balance FROM Accounts           SELECT Balance FROM Accounts
  WHERE AccountID = 1;                   WHERE AccountID = 1;
-- (both see 1000)
UPDATE Accounts SET Balance = 900      UPDATE Accounts SET Balance = 800
  WHERE AccountID = 1;                   WHERE AccountID = 1;
-- ← danger: lost update if not serialized
COMMIT;                                COMMIT;
-- Final balance = 800, but T1's -100 was lost!

-- A serializable scheduler prevents this with locking.
-- With 2PL, T2 waits until T1 commits:
-- S = R1(X), W1(X), C1, R2(X), W2(X), C2  (a serial order)
Simple Example

Serial: "Customer A deposits $100, then Customer B withdraws $200" — one after another, no overlap.

Concurrent: "A deposits while B withdraws at the same time" — operations interleave, but the scheduler must prevent them from corrupting each other's view.

Real-Life Use Case

A ticket booking site (BookMyShow, Ticketmaster) has thousands of concurrent users checking seat availability and booking. The schedule must allow them all to query (interleaved reads) but serialize the actual bookings — otherwise two users could buy the same seat.

Schedule Notation

Schedules are written as sequences: S = R1(X), R2(Y), W1(X), W2(Y), C1, C2. The DBMS scheduler chooses the order, and serializability theory (Topic 5.5) verifies the result is correct.

5.5 Serializability and Recoverability

Definition

Serializability is the correctness criterion for concurrent schedules: a concurrent schedule is correct if its result is equivalent to some serial schedule (transactions run one after another in some order). Recoverability ensures that even if a transaction aborts, the database can be restored to a consistent state.

Types of Serializability

1. Conflict Serializability

  • Two operations conflict if they belong to different transactions, access the same data item, and at least one is a write.
  • A schedule is conflict-serializable if its conflicting operations can be ordered to match a serial schedule.
  • Tested via a precedence graph (a.k.a. serialization graph): if the graph has no cycles, the schedule is conflict-serializable.

2. View Serializability

  • Weaker than conflict serializability (broader class of schedules).
  • Two schedules are view-equivalent if every read operation sees the same value and the final writes are the same.
  • Harder to test — generally NP-complete, so DBMSs usually enforce conflict serializability (easier).

Types of Recoverability

  • Irrecoverable Schedule — dangerous: a transaction reads uncommitted data from another and commits; if the other aborts, the first's reads are invalid.
  • Recoverable Schedule — a transaction only commits after the transactions it read from have committed.
  • Cascadeless Schedule — a transaction only reads committed data. Even safer.
  • Strict Schedule — no transaction reads or writes an item until the transaction that last wrote it has committed/aborted. The safest — enforced by strict 2PL.

Diagram — Precedence Graph (Conflict Serializability)

Figure 5.5 — Precedence graph: a cycle means the schedule is not serializable

Syntax — Recoverable schedule in SQL

SQL — Recoverable transactions 
-- IRRECOVERABLE (dangerous):
-- T1 modifies X but hasn't committed; T2 reads X and COMMITS.
-- If T1 aborts, T2's read was based on invalid data — cannot recover.

-- Session 1 (T1)
START TRANSACTION;
UPDATE Accounts SET Balance = 0 WHERE AccountID = 1;   -- NOT committed yet
-- Session 2 (T2)
SELECT Balance FROM Accounts WHERE AccountID = 1;       -- reads 0 (dirty read!)
COMMIT;
-- If T1 now ROLLBACKs, T2's committed result was based on data that never existed!

-- RECOVERABLE: DBMS prevents this via locking or MVCC
-- T2 blocks until T1 commits (or aborts) — no dirty reads possible.

-- To enforce strictly, set isolation to SERIALIZABLE:
SET TRANSACTION ISOLATION LEVEL SERIALIZABLE;
-- Now transactions are fully serializable AND strict (no dirty reads).
Simple Example

Conflict-serializable: schedule R1(X), W1(X), R2(X), W2(X) — T1 runs first, then T2 — equivalent to serial order T1 → T2. ✓

Not serializable: schedule R1(X), W2(X), W1(X), W2(X) — T1 reads X, T2 writes X, T1 writes X — T1 doesn't see T2's write. This is a lost update. ✗

Real-Life Use Case

In a bank, when two customers withdraw from the same account simultaneously, serializability ensures that one sees the other's committed balance — not a stale snapshot. If the second withdrawal would cause an overdraft, the DBMS aborts it before any inconsistency occurs.

Hierarchy of Schedules

All serial schedules ⊂ conflict-serializable ⊂ view-serializable ⊂ all schedules. DBMSs typically enforce conflict-serializability because it's easy to test (cycle detection in precedence graph) and strict enough for correctness.

5.6 Concurrency Control Mechanisms

Definition

Concurrency control is the DBMS subsystem that coordinates simultaneous transactions so they don't interfere. Without it, concurrent transactions can produce anomalies like lost updates, dirty reads, non-repeatable reads, and phantoms.

Concurrency Anomalies

  • Lost Update — two transactions read the same data, both update, but one update overwrites the other.
  • Dirty Read — a transaction reads uncommitted data from another; if that other aborts, the read was invalid.
  • Non-repeatable Read — a transaction reads the same row twice and sees different values because another transaction updated in between.
  • Phantom Read — a transaction re-runs a query and sees new rows that appeared because another transaction inserted them.

Types of Concurrency Control

  • Lock-Based — transactions acquire locks (shared/exclusive) before reading/writing. Enforced by protocols like 2PL (Topic 5.7).
  • Timestamp-Based — each transaction has a timestamp; operations are ordered by timestamp. Conflicts abort the later transaction.
  • Optimistic (Validation-Based) — transactions run freely, then are validated at commit time. Good when conflicts are rare.
  • Multiversion (MVCC) — multiple versions of each row; readers see a consistent snapshot. Used by PostgreSQL, Oracle, MySQL InnoDB.
  • Snapshot Isolation — a transaction sees a consistent snapshot of the database at its start time.

Diagram — Anomalies Illustrated

Figure 5.6 — Common concurrency anomalies and the mechanisms that prevent them

Syntax — Seeing concurrency control in action

SQL — MVCC & isolation 
-- MVCC in PostgreSQL: readers don't block writers and vice versa
-- Session 1
BEGIN;
SELECT * FROM Accounts WHERE AccountID = 1;   -- sees version 1
-- Session 2
UPDATE Accounts SET Balance = 500 WHERE AccountID = 1;
COMMIT;
-- Session 1 (still open)
SELECT * FROM Accounts WHERE AccountID = 1;   -- REPEATABLE READ → sees version 1
COMMIT;

-- Check current locks (MySQL)
SELECT * FROM information_schema.innodb_locks;
SELECT * FROM information_schema.innodb_lock_waits;

-- Check current locks (PostgreSQL)
SELECT pid, locktype, mode, granted, relation::regclass
FROM pg_locks
WHERE relation IS NOT NULL;

-- See MVCC row versions (PostgreSQL internal)
SELECT xmin, xmax, * FROM Accounts WHERE AccountID = 1;
-- xmin = created by transaction id; xmax = deleted by transaction id
Simple Example

Lost update: Alice and Bob both see $1000, both withdraw $100, but only one deduction applies → balance becomes $900 instead of $800.

Solution: with locking, Alice's transaction holds an exclusive lock on the row; Bob waits; then sees $900 and correctly computes $800.

Real-Life Use Case

Flash sales (e.g., Black Friday, 11.11 in China): thousands of customers try to buy the same product simultaneously. Lock-based or MVCC concurrency control ensures inventory isn't oversold — each successful purchase decrements stock by exactly 1, and failed ones see "sold out."

Higher Isolation = Less Concurrency

SERIALIZABLE prevents all anomalies but serializes transactions. For most apps, READ COMMITTED or REPEATABLE READ (with MVCC) gives the best balance of safety and throughput.

5.7 Locking Protocols (Two-Phase Locking, Timestamp Ordering)

Definition

Locking protocols are rules that govern when transactions acquire and release locks, ensuring schedules are serializable. A lock is a DBMS data structure giving a transaction exclusive or shared access to a data item.

Types of Locks

  • Shared Lock (S) — multiple transactions can hold it for reading. Also called "read lock."
  • Exclusive Lock (X) — only one transaction can hold it, for writing. Also called "write lock."
  • Intention Locks (IS, IX, SIX) — used in multi-granularity locking (row/table/page) to signal intent to lock lower-level items.

Compatibility: S is compatible with S (readers don't block readers); X is compatible with nothing.

Types of Locking Protocols

1. Two-Phase Locking (2PL)

  • Phase 1 (Growing) — transactions acquire locks; releasing is forbidden.
  • Phase 2 (Shrinking) — transactions release locks; acquiring new ones is forbidden.
  • Guarantees conflict-serializability.

2. Strict 2PL (S2PL)

  • Variant: hold all exclusive locks until COMMIT (or ROLLBACK).
  • Guarantees both serializability AND strict recoverability (no dirty reads).
  • The default in most DBMSs.

3. Conservative 2PL

  • Acquire all locks up front, before any operation.
  • Prevents deadlock, but hurts concurrency.

4. Rigorous 2PL

  • Hold ALL locks (S and X) until COMMIT. Even stricter, and easier to reason about.

5. Timestamp Ordering (TO)

  • Each transaction gets a unique timestamp (TS) at start.
  • Each data item has read-TS and write-TS (of last access).
  • If a transaction tries to read/write an item "in the past," it's aborted and restarted.
  • Guarantees serializability, but can cause more aborts (no blocking).

Diagram — 2PL Phases

Figure 5.7 — Two-Phase Locking: growing phase (acquire only) → shrinking phase (release only)

Syntax — Locks in action

SQL — Explicit locks 
-- FOR UPDATE: acquire an exclusive lock (MySQL, PostgreSQL)
START TRANSACTION;
SELECT Balance FROM Accounts
WHERE AccountID = 1
FOR UPDATE;   -- locks the row — other writers must wait

UPDATE Accounts SET Balance = Balance - 100 WHERE AccountID = 1;
COMMIT;       -- lock released, other waiters proceed

-- FOR SHARE / LOCK IN SHARE MODE: acquire a shared lock
START TRANSACTION;
SELECT Balance FROM Accounts
WHERE AccountID = 1
FOR SHARE;    -- allows other readers, blocks writers

COMMIT;

-- NOWAIT / SKIP LOCKED (PostgreSQL, MySQL 8+)
SELECT * FROM Orders
WHERE Status = 'pending'
ORDER BY OrderDate
LIMIT 10
FOR UPDATE SKIP LOCKED;
-- → grabs 10 pending rows that aren't already locked
-- → perfect for job queues / worker patterns!

-- See lock waits (MySQL)
SELECT * FROM performance_schema.data_lock_waits;

-- See lock waits (PostgreSQL)
SELECT pid, wait_event_type, wait_event, query
FROM pg_stat_activity
WHERE wait_event_type = 'Lock';
Simple Example

2PL: T1 acquires S lock on X, reads X. T1 acquires X lock on X, writes X. T1 acquires no more locks — enters shrinking phase, releases X lock, commits.

Timestamp Ordering: T1 (TS=1) reads X. T2 (TS=2) tries to write X, but T1's read-TS=1 < T2's TS=2 → T2 aborts. T2 restarts with a new timestamp.

Real-Life Use Case

A job-queue system (Celery, Sidekiq, or a custom order-processing queue) uses FOR UPDATE SKIP LOCKED to let many workers safely grab different pending jobs — no two workers ever grab the same one, and no one waits unnecessarily. This pattern handles millions of jobs per hour.

2PL vs Timestamp Ordering
  • 2PL: blocking; may deadlock; guaranteed serializable.
  • TO: non-blocking (abort instead); no deadlock; but more aborts and more rollbacks.
  • Most modern DBMSs combine both (hybrid approaches) — 2PL for writes, MVCC for reads.

5.8 Deadlock Handling (Prevention, Detection, Recovery)

Definition

A deadlock occurs when two or more transactions wait for each other in a cycle — each holds a lock the other needs, so none can proceed. Without intervention, they wait forever. The DBMS must prevent, detect, or recover from deadlocks.

Deadlock Handling Strategies

1. Deadlock Prevention — stop deadlocks before they happen:

  • Conservative 2PL — acquire ALL locks at start; no partial locking means no cycles.
  • Timestamp-based schemes:
    • Wait-Die — older transaction waits for younger; younger dies (aborts) if it tries to wait for older. (Older survives.)
    • Wound-Wait — older transaction "wounds" (aborts) younger and takes its lock; younger waits for older. (Older stronger.)
  • Lock ordering — all transactions acquire locks in a fixed global order (e.g., by ID).

2. Deadlock Detection — let deadlocks happen, then find them:

  • Wait-for graph — nodes are transactions; edge Ti → Tj means Ti waits for Tj. A cycle = deadlock.
  • DBMS periodically scans the wait-for graph for cycles.
  • Recovery: abort one transaction in the cycle (the "victim") — the rest proceed.

3. Deadlock Recovery — after detection, break the cycle:

  • Victim selection — abort the transaction with the least work done / fewest locks / lowest priority.
  • Rollback — undo the victim's changes (total or partial rollback).
  • Starvation avoidance — track how often a transaction is aborted; don't abort it too many times.

Diagram — Wait-For Graph with Deadlock Cycle

Figure 5.8 — Wait-for graph: a cycle is a deadlock; the DBMS aborts one transaction to break it

Syntax — Observing and handling deadlocks

SQL — Deadlock in action 
-- Reproduce a deadlock in MySQL/PostgreSQL:
-- Session 1 (T1)
START TRANSACTION;
UPDATE Accounts SET Balance = 1000 WHERE AccountID = 1;  -- locks row 1

-- Session 2 (T2)
START TRANSACTION;
UPDATE Accounts SET Balance = 2000 WHERE AccountID = 2;  -- locks row 2

-- Session 1 (T1) tries to update row 2 — waits for T2
UPDATE Accounts SET Balance = 1500 WHERE AccountID = 2;

-- Session 2 (T2) tries to update row 1 — waits for T1 → DEADLOCK
UPDATE Accounts SET Balance = 2500 WHERE AccountID = 1;

-- One session gets an error:
-- MySQL:      ERROR 1213 (40001): Deadlock found when trying to get lock; try restarting transaction
-- PostgreSQL: ERROR: deadlock detected
-- The DBMS automatically rolls back one transaction.

-- ---------- See deadlock info ----------
-- MySQL
SHOW ENGINE INNODB STATUS\G
-- Look for "LATEST DETECTED DEADLOCK" section

-- PostgreSQL
SELECT * FROM pg_stat_activity WHERE wait_event_type = 'Lock';
-- Look for wait_event = 'deadlock'

-- ---------- Prevent deadlocks ----------
-- 1. Always lock rows in the same order:
START TRANSACTION;
UPDATE Accounts SET Balance = Balance - 100 WHERE AccountID = 1;
UPDATE Accounts SET Balance = Balance + 100 WHERE AccountID = 2;
COMMIT;

-- 2. Use lock timeout (MySQL, PostgreSQL)
SET innodb_lock_wait_timeout = 10;   -- MySQL: 10 seconds
SET lock_timeout = '10s';             -- PostgreSQL

-- 3. Retry on deadlock in application code
-- (catch error → wait random ms → retry transaction)
Simple Example

Deadlock: T1 holds lock on Account A and needs Account B. T2 holds lock on B and needs A. Both wait forever.

Wait-Die: T1 (older) wants B but T2 (younger) holds it → T1 waits. T2 wants A but T1 holds it → T2 dies (aborted). No cycle can form.

Real-Life Use Case

In a multiplayer game, two players trade items at the same time: player A swaps item X for Y, player B swaps Y for X. Without deadlock handling, both transactions freeze. The DBMS detects the wait-for cycle and aborts the younger one (e.g., B) — B is notified and retries automatically with a fresh timestamp.

Wait-Die vs Wound-Wait
  • Wait-Die (older waits for younger; younger dies): more aborts among younger transactions.
  • Wound-Wait (older wounds younger; younger waits): more aborts among younger too, but at a different point.
  • Both are deadlock-free by design (they only abort in one direction).
