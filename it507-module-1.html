1.1 Introduction to Data, Information, and Database

Definition

Data is raw, unprocessed facts and figures with no meaning on their own. It is the basic input that we collect — numbers, text, symbols, or measurements.

Information is data that has been processed, organized, and given meaning and context. It answers questions and helps in decision-making.

Database is an organized collection of related data stored in a structured way so that it can be easily accessed, managed, and updated.

Types

Types of Data:

  • Structured data — organized in rows and columns (e.g., name, age, salary).
  • Semi-structured data — partially organized (e.g., JSON, XML, emails).
  • Unstructured data — no fixed format (e.g., images, videos, audio, text documents).

Types of Databases:

  • Relational databases — use tables (e.g., MySQL, PostgreSQL, Oracle).
  • NoSQL databases — flexible schemas (e.g., MongoDB, Cassandra).
  • Object-oriented databases — store objects (e.g., db4o).
  • Hierarchical databases — tree structure (e.g., IBM IMS).
  • Network databases — graph of records (e.g., IDMS).

Diagram — Data → Information → Database

Figure 1.1 — From raw data to information, stored in a database

Syntax — Storing data in a database

In SQL, we first create a table (structure) and then insert data into it:

SQL 
-- Create a table to store student data
CREATE TABLE Students (
    StudentID INT PRIMARY KEY,
    Name VARCHAR(50),
    Age INT,
    City VARCHAR(50)
);

-- Insert raw data (which becomes information when queried)
INSERT INTO Students (StudentID, Name, Age, City)
VALUES (1, 'Ali', 20, 'Lahore'),
       (2, 'Sara', 22, 'Karachi');

-- Retrieve meaningful information
SELECT Name, Age FROM Students WHERE Age > 20;
Simple Example

Data: "Ali", 20, "Lahore" — just raw values.

Information: "Ali is a 20-year-old student from Lahore who is older than 18." — processed and meaningful.

Database: A Students table storing thousands of such records, searchable and updatable.

Real-Life Use Case

A hospital stores patient records: data = temperature readings (98.6, 101.2). Information = "Patient has fever above 100°F." Database = the hospital's electronic health records system (e.g., Epic, Cerner) that stores all patient data and lets doctors query it instantly.

1.2 Data Administration vs. Database Administration

Definition

Data Administration (DA) is a high-level, business-focused function that manages data as a corporate resource. It focuses on data policies, standards, governance, and data quality across the whole organization.

Database Administration (DBA) is a technical, hands-on function that manages the physical and logical databases — installation, configuration, backup, security, performance tuning, and user access.

Types / Key Differences

AspectData Administration (DA)Database Administration (DBA)
FocusBusiness & data governanceTechnical & operational
ScopeOrganization-wideIndividual database systems
ResponsibilitiesData policies, standards, quality, privacyInstallation, backup, recovery, tuning, security
Reporting ToCIO / CDO (business side)IT Manager / DBA Lead (technical side)
Example TaskDefining a company-wide naming conventionCreating tables, indexes, and users

Diagram — Relationship

Figure 1.2 — DA sets the rules; DBA implements them on the database

Syntax — What a DBA actually does

DA might define a rule: "All user tables must be prefixed with tbl_." The DBA enforces it:

SQL 
-- DBA follows the DA's naming standard
CREATE TABLE tbl_Employees (
    EmpID INT PRIMARY KEY,
    EmpName VARCHAR(100) NOT NULL,
    Department VARCHAR(50)
);
Simple Example

DA: "Every customer record must have a valid email address, and we must keep all data for 7 years for compliance."

DBA: Adds a CHECK constraint on the email column and configures automated backups retained for 7 years.

Real-Life Use Case

In a bank: the Data Administrator decides that all customer data must comply with GDPR and defines a "data retention policy." The Database Administrator then implements encrypted columns, sets up audit logs, and configures nightly backups to satisfy that policy.

1.3 Role and Responsibilities of a Database Administrator (DBA)

Definition

A Database Administrator (DBA) is the IT professional responsible for the installation, configuration, maintenance, security, backup, recovery, and performance of an organization's databases. They make sure data is available, accurate, and secure at all times.

Types of DBAs

  • Production DBA — manages live, running systems (backups, tuning, security).
  • Development DBA — works with developers on schema design and code reviews.
  • Application DBA — focuses on a specific application's database (e.g., SAP DBA).
  • Cloud DBA — manages cloud-hosted databases (AWS RDS, Azure SQL, GCP Cloud SQL).
  • Data Warehouse DBA — handles analytics and reporting databases.

Key Responsibilities

  • Installation & configuration of DBMS software and database instances.
  • Database design — creating schemas, tables, indexes, and relationships.
  • Performance tuning — optimizing slow queries and indexes.
  • Backup & recovery — ensuring data can be restored after a failure.
  • Security — creating users, granting privileges, auditing access.
  • Capacity planning — predicting storage and resource needs.
  • Upgrades & patching — keeping DBMS versions current and secure.
  • Monitoring — watching logs, alerts, and performance metrics 24/7.

Diagram — DBA Responsibilities

Figure 1.3 — Core responsibilities of a Database Administrator

Syntax — Common DBA tasks

SQL 
-- 1. Create a new database instance
CREATE DATABASE CompanyDB;

-- 2. Create a user and grant privileges (security)
CREATE USER 'ali'@'localhost' IDENTIFIED BY 'SecurePass123';
GRANT SELECT, INSERT ON CompanyDB.* TO 'ali'@'localhost';

-- 3. Create a backup (MySQL example, run from shell)
-- $ mysqldump -u root -p CompanyDB > backup_2025.sql

-- 4. Tune a query with an index
CREATE INDEX idx_emp_dept ON tbl_Employees(Department);
Simple Example

A new employee joins a company. The DBA creates a database account for them, gives read-only access to the Employees table, and enables auditing so every query they run is logged.

Real-Life Use Case

At Amazon, a DBA manages hundreds of databases. When Black Friday traffic spikes, the DBA adds read replicas, tunes slow product-search queries, and monitors for deadlocks — all to keep the shopping cart and checkout system running smoothly.

1.4 Database Management System (DBMS) — Definition and Overview

Definition

A Database Management System (DBMS) is software that sits between users/applications and the physical database. It lets users define, create, manipulate, and control access to a database — without worrying about how data is stored on disk.

Types of DBMS

  • Relational (RDBMS) — tables with rows and columns (MySQL, Oracle, SQL Server, PostgreSQL).
  • Object-Oriented — stores objects (db4o, ObjectDB).
  • Object-Relational — hybrid (PostgreSQL has object features).
  • Hierarchical — tree structure (IBM IMS).
  • Network — graph structure (IDMS).
  • NoSQL — document/key-value/column/graph (MongoDB, Redis, Cassandra, Neo4j).

Diagram — DBMS Architecture Overview

Figure 1.4 — DBMS sits between users and the physical database

Key Functions of a DBMS

  • Data Definition — create/modify schema via DDL.
  • Data Manipulation — query and update via DML.
  • Data Security — authentication and authorization.
  • Concurrency Control — handle multiple users safely.
  • Backup and Recovery — protect against failures.
  • Data Integrity — enforce constraints (keys, checks).
  • Performance Optimization — indexes, query plans.

Syntax — Talking to a DBMS

All interaction happens through the DBMS using a language (usually SQL):

SQL 
-- DDL: define structure (DBMS stores this in its catalog)
CREATE TABLE Courses (
    CourseID INT PRIMARY KEY,
    Title VARCHAR(100),
    Credits INT
);

-- DML: manipulate data
INSERT INTO Courses VALUES (503, 'Database Administration', 3);

-- DQL: query data
SELECT * FROM Courses WHERE Credits = 3;
Simple Example

When you type a query into MySQL Workbench, the DBMS (MySQL) parses it, checks permissions, finds the data on disk, and returns the result. You never directly touch the data files — the DBMS handles it all.

Real-Life Use Case

Every time you log into Facebook, a DBMS (MySQL/TAO) checks your credentials, fetches your feed, and records your activity — all within milliseconds. The DBMS hides billions of rows and complex storage from the application code.

1.5 Development and Management of Databases for Information Systems

Definition

Database development is the process of planning, designing, building, and deploying a database to support an information system. Database management is the ongoing operation and maintenance of that database after deployment — backups, tuning, security, upgrades, and monitoring.

Phases of Database Development (SDLC for Databases)

  1. Requirements gathering — understand what data the business needs.
  2. Conceptual design — ER diagrams, entities, relationships.
  3. Logical design — tables, keys, normalization.
  4. Physical design — indexes, storage, partitioning.
  5. Implementation — CREATE TABLE, constraints, sample data.
  6. Testing — data integrity, query performance, security tests.
  7. Deployment — go live, migrate data, hand off to DBA.
  8. Maintenance — monitor, tune, backup, upgrade.

Diagram — Database Development Lifecycle

Figure 1.5 — Database development lifecycle (build → deploy → maintain → improve)

Syntax — Build then manage

SQL 
-- DEVELOPMENT: create the database and a table
CREATE DATABASE LibraryDB;
USE LibraryDB;

CREATE TABLE Books (
    BookID INT PRIMARY KEY AUTO_INCREMENT,
    Title VARCHAR(200) NOT NULL,
    Author VARCHAR(100),
    YearPublished INT
);

-- MANAGEMENT: after go-live, add an index for performance
CREATE INDEX idx_books_author ON Books(Author);

-- Periodic maintenance
-- $ mysqldump -u root -p LibraryDB > library_backup.sql
Simple Example

A school wants a library system. The development team builds Books, Members, and Loans tables. After launch, the management team (DBA) adds indexes, schedules daily backups, and monitors for slow queries.

Real-Life Use Case

A hospital's patient management system: developers build the schema (patients, appointments, prescriptions). The DBA manages it after go-live — ensuring HIPAA-compliant access controls, 24/7 uptime, and daily encrypted backups.

1.6 Types of Database Users and Their Interfaces

Definition

Database users are the different people (and applications) who interact with a database. Each type has different skills, needs, and access patterns — so they are given different interfaces (ways of talking to the DBMS).

Types of Database Users

  1. Naive / Parametric Users — use pre-written forms or menus; no SQL knowledge. Example: a bank teller checking an account balance.
  2. Application Programmers — write programs (Java, Python) that call the database via APIs. Example: a mobile banking app developer.
  3. Sophisticated Users — write complex queries and reports; use SQL directly. Example: a business analyst running ad-hoc reports.
  4. Specialized Users — build complex, specialized database applications (CAD, AI, GIS). Example: a GIS engineer querying spatial data.
  5. DBA — the administrator who manages the whole system.

Types of Interfaces

  • Menu-based interface — options selected from menus (e.g., ATM screen).
  • Forms-based interface — fill-in-the-blank forms (e.g., bank teller software).
  • Command-line interface (CLI) — typed commands (e.g., mysql> shell, psql).
  • GUI tools — graphical clients (e.g., MySQL Workbench, pgAdmin, DBeaver).
  • API / Programming interface — ODBC, JDBC, or language-specific drivers.
  • Natural-language interface — plain-English queries (emerging, powered by AI).

Diagram — Users → Interfaces → DBMS

Figure 1.6 — Different users use different interfaces, all reaching the same DBMS

Syntax — Same query, different interfaces

SQL & API examples 
-- SOPHISTICATED USER: runs SQL directly in a CLI or SQL editor
SELECT Name, Balance FROM Accounts WHERE AccountID = 1001;

-- APPLICATION PROGRAMMER: calls the same query via JDBC (Java)
String sql = "SELECT Name, Balance FROM Accounts WHERE AccountID = ?";
PreparedStatement ps = conn.prepareStatement(sql);
ps.setInt(1, 1001);
ResultSet rs = ps.executeQuery();

-- NAIVE USER: never sees SQL — clicks "Check Balance" in the ATM menu
-- (the ATM app runs the query above on the user's behalf)
Simple Example

At a bank: a customer uses an ATM menu (naive), a teller uses a forms-based app (naive), a developer writes JDBC code (programmer), an analyst runs SQL in a GUI (sophisticated), and the DBA uses admin tools to tune indexes.

Real-Life Use Case

In Uber's ecosystem: riders use the app (menu/API interface), drivers use a separate app (API interface), data analysts query trip data in Looker/SQL (sophisticated), and platform DBAs manage the hundreds of database clusters (admin interface).

1.7 Database Environment and Architecture (Three-Schema Architecture)

Definition

The three-schema architecture (also called the ANSI/SPARC architecture, 1975) is a standard way to separate how users see the database from how it is physically stored. It has three levels:

  • External (View) Level — how each user/application sees the data. Multiple external views are possible.
  • Conceptual (Logical) Level — the community view: the full logical structure (tables, relationships, constraints).
  • Internal (Physical) Level — how data is actually stored on disk (files, indexes, pages).

Why It Matters

  • Data independence — change the physical storage without breaking applications.
  • Security — each user sees only their view; sensitive columns can be hidden.
  • Simplification — users don't need to know physical storage details.
  • Customization — different departments get different views of the same data.

Diagram — Three-Schema Architecture

Figure 1.7 — Three-schema architecture: Views → Logical Schema → Physical Storage

Syntax — Creating views (external level) over a logical table

SQL 
-- CONCEPTUAL LEVEL: the full table (all columns)
CREATE TABLE Employees (
    EmpID INT PRIMARY KEY,
    Name VARCHAR(100),
    Salary DECIMAL(10,2),
    Department VARCHAR(50),
    Email VARCHAR(100)
);

-- EXTERNAL LEVEL: HR sees only name and department
CREATE VIEW vw_HR_View AS
SELECT Name, Department FROM Employees;

-- EXTERNAL LEVEL: Finance sees only name and salary
CREATE VIEW vw_Finance_View AS
SELECT Name, Salary FROM Employees;

-- Now HR can't see salary, Finance can't see email — security by view
SELECT * FROM vw_HR_View;      -- only 2 columns visible
SELECT * FROM vw_Finance_View; -- only 2 columns visible
Simple Example

A Students table has 20 columns. The exam office gets a view with only RollNo, Name, Marks. The fee office gets a view with only RollNo, Name, FeeStatus. Both query their own views — but the underlying table is the same one on disk.

Real-Life Use Case

In a hospital: doctors see a view with patient name, diagnosis, prescription. Billing staff see a view with patient name, services, amount. Neither can see the other's sensitive data — but both views pull from the same Patients table.

1.8 Centralized vs. Distributed Database Systems

Definition

A centralized database stores all data at a single location (one server or data center). All users access that one system.

A distributed database stores data across multiple locations (sites) that are connected by a network. Users access data transparently — they don't need to know where it physically lives.

Types

Centralized database types:

  • Single-tier — DBMS and app on one machine (small systems).
  • Two-tier (client-server) — clients connect to a central DB server.
  • Three-tier — client → application server → DB server (common in web apps).

Distributed database types:

  • Homogeneous — all sites run the same DBMS (e.g., all MySQL).
  • Heterogeneous — different DBMSs at different sites (e.g., Oracle + MySQL + PostgreSQL).
  • Federated — independent databases integrated into one virtual view.
  • Replicated — full copies of data at every site.
  • Partitioned / Sharded — data split across sites (each site holds a subset).

Comparison

AspectCentralizedDistributed
LocationSingle siteMultiple sites
CostLower initial costHigher setup & network cost
ComplexitySimple to manageComplex (coordination, replication)
ScalabilityVertical (bigger server)Horizontal (add more nodes)
Fault toleranceSingle point of failureHighly available (replicas)
LatencyLow for nearby usersLow for local users, varies globally
Best forSmall/medium businessesLarge enterprises, global apps

Diagram — Both Architectures Side by Side

Figure 1.8 — Centralized (single server) vs Distributed (multiple networked servers)

Syntax — Setup example

SQL — Centralized 
-- CENTRALIZED: one server holds everything
CREATE DATABASE SchoolDB;
USE SchoolDB;

CREATE TABLE Students (
    StudentID INT PRIMARY KEY,
    Name VARCHAR(100),
    City VARCHAR(50)
);
SQL — Distributed (partitioned) 
-- DISTRIBUTED: data split across sites by City (partitioning)
-- Site A (Lahore server): stores Lahore students only
CREATE TABLE Students_Lahore (
    StudentID INT PRIMARY KEY,
    Name VARCHAR(100),
    City VARCHAR(50) DEFAULT 'Lahore'
);

-- Site B (Karachi server): stores Karachi students only
CREATE TABLE Students_Karachi (
    StudentID INT PRIMARY KEY,
    Name VARCHAR(100),
    City VARCHAR(50) DEFAULT 'Karachi'
);

-- Applications query the appropriate site based on the user's city
-- (or use a distributed DBMS like Cassandra that handles this automatically)
Simple Example

Centralized: A small shop's billing system runs on one desktop computer in the back office.

Distributed: A supermarket chain with 50 branches — each branch has its own database server (for local checkout speed), and they sync sales data to a central warehouse database nightly.

Real-Life Use Case

Centralized: A university's student records on one campus server. Distributed: Netflix stores user data across AWS regions worldwide — your profile is replicated in multiple data centers so any outage doesn't stop you from watching. Google Spanner is a globally distributed database that keeps Google's data consistent across continents.
