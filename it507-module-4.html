4.1 Data Structures in DBMS

Definition

Data structures in a DBMS are the internal structures the database engine uses to organize and access data efficiently on disk and in memory. They're not the same as "tables" (which are logical) — these are the physical structures the DBMS builds behind the scenes to make queries fast.

Types of Data Structures in DBMS

  • Files — the top-level physical container (e.g., a data file for a table).
  • Pages (Blocks) — fixed-size units of storage (typically 4–16 KB) that hold records.
  • Records (Rows) — the actual data rows stored inside pages.
  • Indexes — auxiliary structures (B+ trees, hash tables) for fast lookups.
  • Heaps — unordered collections of pages.
  • B+ Trees — balanced tree structures for range queries and ordered scans.
  • Hash Tables — for direct key-based lookups (equality searches).
  • Bitmaps — compact representations for low-cardinality columns.
  • Log Buffers — in-memory buffers for write-ahead logging (WAL).
  • Buffer Pool — memory cache for frequently accessed pages.

Diagram — DBMS Data Structure Hierarchy

Figure 4.1 — DBMS data structure hierarchy: database → tables/indexes → pages → records → fields

Syntax — Seeing the physical structures

SQL — See structures 
-- See the physical files behind a table (MySQL InnoDB)
SHOW TABLE STATUS FROM SchoolDB LIKE 'Students';
-- File: Students.ibd — holds data + primary index

-- See the indexes on a table
SHOW INDEX FROM Students;

-- See how many pages a table has (PostgreSQL)
SELECT relname, relpages, reltuples
FROM pg_class
WHERE relname = 'students';

-- See buffer pool stats (MySQL)
SHOW ENGINE INNODB STATUS\G
Simple Example

A table Students with 1 million rows is stored as thousands of pages on disk, each holding many records. A B+ tree index sits alongside, mapping each StudentID to the page where its record lives — so lookups are fast even with millions of rows.

Real-Life Use Case

Every time Amazon's product search runs, it uses B+ tree indexes to find matching products. The system doesn't scan all 500 million products — the index points directly to the pages holding the relevant records, so results return in milliseconds.

4.2 File Organizations — Heap, Sequential, Indexed, Hashed

Definition

File organization refers to how records are arranged in a file on disk. Different organizations are better for different operations — some are fast for inserting, others for searching or sorting. The DBMS chooses the file organization based on the workload.

Types of File Organizations

1. Heap File (Unordered)

  • Records stored in no particular order.
  • Insert: very fast (append to end).
  • Search: slow (must scan all pages).
  • Delete: leaves holes (uses free-space map).
  • Best for: bulk loads, tables with no frequent lookups.

2. Sequential File (Ordered)

  • Records stored sorted by a search key.
  • Insert: must find the right slot — slow.
  • Search: fast — binary search or direct position.
  • Range queries: excellent — just scan sequentially.
  • Best for: master files that change rarely but are queried often.

3. Indexed File

  • Records stored in some order plus an index structure (B+ tree) that points to them.
  • Search: very fast via index.
  • Insert: fast — append + update index.
  • Range queries: fast.
  • Best for: general-purpose OLTP databases (the default in most DBMSs).

4. Hashed File

  • Records placed using a hash function on the key.
  • Equality search (WHERE id = 123): extremely fast — O(1).
  • Range queries: terrible — hash order is random.
  • Insert: fast unless the bucket is full (collision).
  • Best for: exact-match lookups (e.g., user sessions, caches).

Diagram — Four File Organizations Compared

Figure 4.2 — Four file organizations and their trade-offs

Syntax — Choosing file organization

SQL — Storage engines & organization 
-- MySQL InnoDB uses a clustered B+ tree by default (an indexed file)
CREATE TABLE Students (
    StudentID INT PRIMARY KEY,
    Name      VARCHAR(100)
) ENGINE = InnoDB;

-- MySQL MEMORY engine uses hashing by default
CREATE TABLE Sessions (
    SessionID CHAR(36) PRIMARY KEY,
    UserID    INT,
    ExpiresAt DATETIME
) ENGINE = MEMORY;

-- PostgreSQL: heap file by default
CREATE TABLE Logs (
    LogID    BIGSERIAL PRIMARY KEY,
    Message  TEXT,
    LogTime  TIMESTAMP DEFAULT NOW()
);  -- stored as an unordered heap

-- Add an index (a B+ tree) to a heap table
CREATE INDEX idx_logs_time ON Logs(LogTime);

-- Choose hash index (PostgreSQL)
CREATE INDEX idx_sessions_user ON Sessions USING HASH (UserID);
Simple Example

Heap: a log file — you always append, rarely query by key.

Sequential: a phone directory — sorted by name, easy to find.

Indexed: a library catalog — sorted plus card index.

Hashed: a coat check — you give a ticket (key) and get your coat (record) instantly.

Real-Life Use Case

A user session system needs instant lookups by SessionID (no range queries), so it uses a hashed organization. A transaction table is queried by date range, so it uses a sequential or indexed file. A pure event-log table just appends, so heap is perfect.

4.3 Indexing — Primary, Secondary, Clustered, Non-Clustered

Definition

An index is an auxiliary data structure that speeds up data retrieval by providing quick access paths. Think of it as a book's table of contents — instead of reading every page to find a topic, you look it up and jump straight there. Indexes trade extra storage and slightly slower writes for much faster reads.

Types of Indexes

By key uniqueness:

  • Primary Index — built on the primary key column; one per table; values are unique.
  • Secondary Index — built on non-key columns; can be multiple; allows duplicate values.

By physical organization:

  • Clustered Index — determines the physical order of rows in the table. Only one per table. In MySQL InnoDB, the primary key is the clustered index.
  • Non-Clustered Index — separate structure with a pointer to the row's location. Multiple allowed per table. Cannot be one per table.

Other useful types:

  • Unique Index — enforces uniqueness (like primary key but can allow one NULL).
  • Composite / Multi-column Index — built on two or more columns.
  • Covering Index — contains all columns a query needs, so table access isn't needed.
  • Full-text Index — for searching inside text.
  • Spatial Index — for geographic coordinates.
  • Bitmap Index — for low-cardinality columns (e.g., gender).

Diagram — Clustered vs Non-Clustered Index

Figure 4.3 — Clustered index stores data in order; non-clustered index points to rows

Syntax — Creating different indexes

SQL — Index creation 
-- Table with a primary key (becomes the clustered index in InnoDB)
CREATE TABLE Employees (
    EmpID     INT PRIMARY KEY,   -- clustered index on EmpID
    Name      VARCHAR(100),
    Email     VARCHAR(150),
    DeptID    INT,
    Salary    DECIMAL(10,2)
);

-- Non-clustered index on Name (for fast lookups by name)
CREATE INDEX idx_employees_name ON Employees(Name);

-- Unique index on Email (enforces uniqueness + speeds lookups)
CREATE UNIQUE INDEX idx_employees_email ON Employees(Email);

-- Composite index on (DeptID, Salary)
-- Perfect for: WHERE DeptID = ? AND Salary > ?
CREATE INDEX idx_dept_salary ON Employees(DeptID, Salary);

-- Covering index — includes all columns a query needs
CREATE INDEX idx_cover_dept ON Employees(DeptID, Name, Salary);
-- Now: SELECT Name, Salary FROM Employees WHERE DeptID = 10
-- → answered entirely from the index, no table access!

-- Full-text index (MySQL) for text search
CREATE FULLTEXT INDEX idx_desc ON Products(Description);

-- SQL Server syntax for a clustered vs non-clustered index
CREATE CLUSTERED INDEX idx_clustered_emp ON Employees(EmpID);
CREATE NONCLUSTERED INDEX idx_nonclustered_name ON Employees(Name);

-- See all indexes on a table
SHOW INDEX FROM Employees;
Simple Example

Clustered: in a dictionary, the words are physically sorted — one sorted list, no extra index.

Non-clustered: a book's back-of-book index — "Topic X → page 47" — the pages themselves aren't in alphabetical order.

Covering index: a cheat-sheet listing just what you need, so you never need the full table.

Real-Life Use Case

An e-commerce site has 10 million products. Customers search by category + price range. A composite non-clustered index on (CategoryID, Price) makes those searches take milliseconds instead of seconds. The primary key ProductID is clustered for fast lookups by ID.

Too Many Indexes Is Bad

Each index consumes storage and slows down every INSERT/UPDATE/DELETE (the DBMS has to maintain all indexes). Aim for indexes on columns used in WHERE, JOIN, and ORDER BY — not on every column.

4.4 B-Trees and B+ Trees

Definition

B-Tree (Balanced Tree) and B+ Tree are self-balancing search trees optimized for disk-based storage. They keep all leaf nodes at the same depth, ensuring O(log n) search, insert, and delete — even for billions of keys.

  • B-Tree — every node stores both keys and data pointers. Internal nodes also hold data.
  • B+ Tree — internal nodes store only keys (as a road-map); all data lives in the leaf level. Leaves are linked together in a chain, enabling fast range scans. This is the default index structure in nearly every modern DBMS.

Key Properties

  • Balanced — all leaves at the same depth.
  • High fan-out — each node holds hundreds of keys, so the tree is very shallow (typically 3–4 levels for millions of rows).
  • Ordered — leaves are sorted; range queries (BETWEEN, >, <) are efficient.
  • Logarithmic — operations are O(log n), with few disk reads.

Diagram — B+ Tree Structure

Figure 4.4 — B+ Tree: root → internal nodes → linked leaf nodes holding data

Syntax — B+ tree in action

SQL — B+ tree index 
-- The DBMS automatically builds a B+ tree when you CREATE INDEX
CREATE INDEX idx_orders_date ON Orders(OrderDate);

-- These queries use the B+ tree:
SELECT * FROM Orders WHERE OrderDate = '2025-01-15';   -- equality
SELECT * FROM Orders WHERE OrderDate BETWEEN '2025-01-01' AND '2025-01-31';  -- range
SELECT * FROM Orders ORDER BY OrderDate LIMIT 10;       -- sorted retrieval

-- See the B+ tree depth (MySQL InnoDB)
SELECT index_name, stat_name, stat_value
FROM mysql.innodb_index_stats
WHERE table_name = 'orders' AND stat_name = 'n_leaf_pages';

-- SQL Server: see index depth
SELECT i.name, i.type_desc, s.page_count
FROM sys.indexes i
JOIN sys.dm_db_partition_stats s ON i.object_id = s.object_id
WHERE OBJECT_NAME(i.object_id) = 'Orders';
Simple Example

B+ tree lookup: find id = 35: root says "go right of 25, left of 50" → internal says "go left of 40" → leaf [35, 40] contains 35. Just 3 disk reads instead of scanning millions of rows!

Range query: WHERE id BETWEEN 15 AND 40: find leaf with 15, then follow leaf chain → 20, 25, 30, 35, 40. Fast sequential read.

Real-Life Use Case

Every major database uses B+ trees for indexes: MySQL InnoDB, PostgreSQL, Oracle, SQL Server, SQLite. When you CREATE INDEX, a B+ tree is built behind the scenes. Queries like "find orders from January" use the leaf-chain range scan — fast on any scale.

B-Tree vs B+ Tree
  • B-Tree: data pointers in all nodes. Good for exact lookups, but range scans are slower (must traverse up and down).
  • B+ Tree: data only in leaves, leaves linked. Great for range scans, disk-friendly. The default for almost all DBMSs.

4.5 Hashing Techniques

Definition

Hashing is a technique that computes a hash value from a key using a hash function, and uses that value to determine where the record is stored (or found). Hashing is O(1) for exact-match lookups but poor for range queries.

Types of Hashing

  • Static Hashing — fixed number of buckets. Simple but bad when the dataset grows (long overflow chains).
  • Dynamic Hashing — buckets grow/shrink with the data. Two main variants:
    • Extendible Hashing — uses a directory of pointers; doubles only the directory, not all buckets.
    • Linear Hashing — splits buckets one by one as needed; no directory.
  • Consistent Hashing — used in distributed systems (Cassandra, DynamoDB) to distribute keys across many nodes with minimal reshuffling when nodes join/leave.

Collision resolution:

  • Open Addressing — probe the next slot (linear, quadratic, double hashing).
  • Chaining — each bucket holds a list of overflow records.
  • Overflow Buckets — extra pages chained to full buckets.

Diagram — Static Hashing with Buckets

Figure 4.5 — Static hashing: h(key) = key mod 4 distributes keys into buckets

Syntax — Hash indexes and their limitations

SQL — Hash index 
-- PostgreSQL: create a HASH index
CREATE INDEX idx_sessions_id ON Sessions USING HASH (SessionID);

-- Very fast: exact lookup
SELECT * FROM Sessions WHERE SessionID = 'abc123';
-- → uses hash index (O(1) instead of O(log n))

-- Do NOT use a hash index for range queries
SELECT * FROM Sessions WHERE SessionID > 'abc';
-- → forces a full scan (hash indexes can't answer ranges)

-- MySQL MEMORY engine is hashed by default
CREATE TABLE Cache (
    CacheKey VARCHAR(100) PRIMARY KEY,
    Value    TEXT
) ENGINE = MEMORY;
-- Lookups on CacheKey are O(1) hash lookups
Simple Example

Static hashing: 4 buckets, h(key) = key mod 4. Key 7 → bucket 3, key 10 → bucket 2, key 12 → bucket 0.

Collision: if key 6 also goes to bucket 2 and it's full, the record goes into an overflow bucket chained to bucket 2.

Real-Life Use Case

Session stores (Redis) use hashing for O(1) lookups by session ID. Cassandra and DynamoDB use consistent hashing to distribute billions of keys across thousands of nodes — when a node is added or removed, only ~1/N of the keys need to move.

Hash vs B+ Tree — Choose Wisely

Hash indexes excel at exact-match lookups but cannot answer range or ORDER BY queries. If your query is WHERE id = ?, hash is ideal. If it's WHERE date BETWEEN ..., use a B+ tree.

4.6 Storage Structures — Records, Blocks, and Files

Definition

Storage structures describe how data is physically organized on disk — from the smallest unit (bytes) to records, blocks (pages), and files. Understanding this hierarchy explains why some operations are fast and others are slow.

The Storage Hierarchy

  • Field — the smallest unit; one column value in a row.
  • Record (Row / Tuple) — one complete entity; a set of fields. Fixed-length or variable-length.
  • Block (Page) — the DBMS reads/writes in blocks, typically 4 KB, 8 KB, or 16 KB. One block contains many records.
  • File — a collection of blocks; e.g., a table's data file.
  • Tablespace — a logical grouping of files (Oracle, PostgreSQL).

Key Concepts

  • Block size — measured in bytes; choice impacts performance (bigger = fewer I/Os but more wasted space).
  • Blocking factor — number of records per block.
  • Record layout — how fields are packed inside a record; includes record header and null bitmap.
  • Slotted page — a page design with a slot directory pointing to each record; supports variable-length records.
  • Row migration — when a row grows and no longer fits in its original block, it's moved to a new block (with a pointer).

Diagram — File → Blocks → Records → Fields

Figure 4.6 — File → blocks → records → fields (the DBMS reads/writes whole blocks)

Syntax — Inspecting storage structures

SQL — Storage inspection 
-- MySQL: see page size and row format
SHOW VARIABLES LIKE 'innodb_page_size';      -- 16384 (16 KB)
SHOW TABLE STATUS FROM SchoolDB LIKE 'Students';
-- Shows: Data_length (data size), Index_length (indexes), Row_format

-- PostgreSQL: see table and toast sizes
SELECT pg_size_pretty(pg_total_relation_size('students')) AS total_size,
       pg_size_pretty(pg_relation_size('students'))       AS table_size,
       pg_size_pretty(pg_indexes_size('students'))        AS indexes_size;

-- PostgreSQL: block size
SHOW block_size;   -- typically 8192 (8 KB)

-- SQL Server: page size is always 8 KB
SELECT * FROM sys.dm_db_page_info(DB_ID(), 1, 1, 'DETAILED');
-- Inspect a specific page's contents

-- See record count vs page count
SELECT relname, relpages, reltuples
FROM pg_class
WHERE relname = 'students';
Simple Example

A table with 10,000 rows, each ~200 bytes, on an 8 KB page: ~40 records fit per block, so the table occupies ~250 blocks (≈2 MB). A full scan reads 250 blocks — that's why adding indexes (fewer blocks to read) is so powerful.

Real-Life Use Case

A DBA noticing slow reports sees that the Orders table is 50 GB with an average row of 2 KB. Most queries only need (OrderID, CustomerID, Total). So they create a covering index — now queries read just a few KB per page instead of 2 KB per row across the full table. Performance jumps 50×.

Why Block Size Matters

The DBMS reads/writes in whole blocks, not individual rows. Larger blocks (16 KB) mean fewer I/Os for sequential scans, but more wasted space per row. Smaller blocks (4 KB) mean more I/Os but less wasted space. Most modern DBMSs default to 8–16 KB.

4.7 Buffer Management

Definition

Buffer management is the DBMS subsystem that decides which pages to keep in memory and which to evict to disk. Since disk I/O is thousands of times slower than RAM, the buffer pool is the single most critical resource for database performance.

Core Concepts

  • Buffer Pool — a fixed-size region of RAM holding pages loaded from disk.
  • Buffer Frame — one slot in the pool; holds one page + metadata (dirty bit, pin count, last-access time).
  • Page Table — maps a (file, page number) to a buffer frame.
  • Dirty Page — a page modified in memory but not yet written to disk.
  • Pin / Pin Count — a page in use cannot be evicted until its pin count drops to 0.
  • Eviction Policy — which page to swap out when the pool is full.

Common Eviction Policies

  • LRU (Least Recently Used) — evict the page not used for the longest time. Popular, simple.
  • Clock (Second-chance) — a circular approximation of LRU. Used in many DBMSs.
  • MRU (Most Recently Used) — sometimes better for scans.
  • LRU-K — considers the last K accesses, better than plain LRU.
  • ARC (Adaptive Replacement Cache) — adapts between LRU and LFU. Used in modern systems (ZFS, some DBMSs).
  • 2Q — two queues (hot / cold) for better prediction.

Diagram — Buffer Pool Architecture

Figure 4.7 — Buffer pool holds hot pages in RAM; cold pages are evicted to disk

Syntax — Configuring and monitoring the buffer pool

SQL — Buffer pool config 
-- MySQL: how big is the buffer pool?
SHOW VARIABLES LIKE 'innodb_buffer_pool_size';
-- Typical: 50–80% of total RAM on a dedicated DB server

-- Set it at runtime (also edit my.cnf to persist)
SET GLOBAL innodb_buffer_pool_size = 8 * 1024 * 1024 * 1024;   -- 8 GB

-- See buffer pool hit ratio (higher is better, > 99%)
SHOW ENGINE INNODB STATUS\G
-- Look for "Buffer pool hit rate"

-- PostgreSQL: shared_buffers (in postgresql.conf)
SHOW shared_buffers;   -- e.g., '4GB'

-- See hit ratio
SELECT
    sum(heap_blks_hit) AS heap_hits,
    sum(heap_blks_read) AS heap_reads,
    round(100.0 * sum(heap_blks_hit) / nullif(sum(heap_blks_hit + heap_blks_read), 0), 2) AS hit_ratio_pct
FROM pg_statio_user_tables;

-- SQL Server: buffer pool usage
SELECT
    COUNT(*) * 8 / 1024 AS buffer_pool_mb
FROM sys.dm_os_buffer_descriptors;

-- Check top tables by buffer usage
SELECT TOP 10
    OBJECT_NAME(p.object_id) AS table_name,
    COUNT(*) * 8 / 1024 AS mb_in_buffer
FROM sys.dm_os_buffer_descriptors bd
JOIN sys.allocation_units a ON bd.allocation_unit_id = a.allocation_unit_id
JOIN sys.partitions p ON a.container_id = p.hobt_id
GROUP BY p.object_id
ORDER BY mb_in_buffer DESC;
Simple Example

Server has 32 GB RAM. You set the buffer pool to 24 GB. Hot tables fit fully in RAM, so 99% of queries hit the buffer pool (no disk I/O).

If a big analytical query scans a 100 GB table, it fills the pool with cold pages and evicts your hot pages. This is why OLTP and OLAP workloads are often split across different systems.

Real-Life Use Case

Amazon Aurora, MySQL, SQL Server, and PostgreSQL all dedicate a large buffer pool. In a production e-commerce database, "buffer pool hit ratio" is one of the top 3 metrics a DBA watches — anything below 95% signals a RAM shortage and requires adding more memory or tuning queries.

Don't Overallocate

Setting the buffer pool too large (close to total RAM) causes the OS to swap — which is catastrophically slow. Leave enough RAM for the OS and other processes. Typical: 50–80% of total RAM on a dedicated DB server.
