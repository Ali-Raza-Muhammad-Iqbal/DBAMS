6.1 Database Programming — Embedded SQL, Dynamic SQL

Definition

Database programming means writing application code that talks to a database — sending queries, fetching results, handling errors. There are two main styles: embedded SQL (SQL written directly inside a host language like C, COBOL, or Java) and dynamic SQL (SQL strings built and executed at runtime).

Types

1. Embedded SQL (Static SQL)

  • SQL statements are hard-coded in the host language and compiled together.
  • The DBMS knows the exact SQL at compile time, so it can optimize and pre-validate.
  • Syntax: statements prefixed with EXEC SQL in C/COBOL; or in Java with JDBC's prepareStatement().
  • Pros: fast (precompiled), type-safe, secure (no injection).
  • Cons: queries fixed at compile time; can't handle runtime-varying queries.

2. Dynamic SQL

  • SQL strings are built at runtime — usually from user input or config.
  • The DBMS parses and optimizes each time.
  • Syntax: EXEC SQL PREPARE ... EXECUTE IMMEDIATE in embedded; or in applications, Statement.executeQuery(String sql) in JDBC.
  • Pros: flexible (query structure can change at runtime).
  • Cons: slower (parse each time), risk of SQL injection if not parameterized.

3. Stored Procedures / Functions (also covered in Module 3.9)

  • Programmable routines stored inside the DBMS, callable from any language.
  • Best of both: precompiled + flexible + reusable.

Diagram — Embedded vs Dynamic SQL Flow

Figure 6.1 — Embedded SQL is precompiled; Dynamic SQL is built at runtime

Syntax — Embedded SQL (C) vs Dynamic SQL (Java)

C — Embedded SQL 
// Embedded SQL in C — the SQL is compiled into the binary
#include 

int main() {
    EXEC SQL BEGIN DECLARE SECTION;
        int    empId;
        char   name[100];
        double salary;
    EXEC SQL END DECLARE SECTION;

    EXEC SQL CONNECT TO 'companydb' USER 'ali' USING 'pass';

    empId = 101;
    // ↓ Static SQL: known at compile time
    EXEC SQL SELECT Name, Salary INTO :name, :salary
             FROM Employees
             WHERE EmpID = :empId;

    printf("Name: %s, Salary: %.2f\n", name, salary);

    EXEC SQL COMMIT;
    EXEC SQL DISCONNECT;
    return 0;
}
Java — Dynamic SQL (JDBC) 
// Dynamic SQL in Java using JDBC
import java.sql.*;

public class DynamicQuery {
    public static void main(String[] args) throws Exception {
        Connection conn = DriverManager.getConnection(
            "jdbc:mysql://localhost:3306/companydb", "ali", "pass");

        // Build the query dynamically from a runtime value
        String table = "Employees";           // could come from user input
        String sql   = "SELECT * FROM " + table + " WHERE Salary > ?";

        // Use PreparedStatement to avoid SQL injection (see 6.8)
        PreparedStatement ps = conn.prepareStatement(sql);
        ps.setDouble(1, 50000);
        ResultSet rs = ps.executeQuery();

        while (rs.next()) {
            System.out.println(rs.getString("Name") + " — " + rs.getDouble("Salary"));
        }
        rs.close(); ps.close(); conn.close();
    }
}
Simple Example

Embedded: a payroll program that always queries the same Employees table by ID — hard-coded SQL, precompiled, fast.

Dynamic: an admin tool that lets you build a custom query (SELECT * FROM ... WHERE ...) at runtime — flexible, but must be parameterized.

Real-Life Use Case

Banking core systems (COBOL + DB2) use embedded SQL for fixed operations like "transfer funds." Analytics dashboards (Tableau, Looker) use dynamic SQL — they generate custom queries based on filters the user picks at runtime.

Best Practice

Even when using dynamic SQL, always use PreparedStatement (or parameterized queries) with ? placeholders. Never concatenate user input directly into SQL strings (see Topic 6.8).

6.2 Database Connectivity (ODBC, JDBC)

Definition

Database connectivity is the layer of software that lets applications written in various languages talk to various database systems. Without it, every app would need custom code for each DBMS. Standards like ODBC and JDBC provide a common interface.

Types of Connectivity APIs

1. ODBC (Open Database Connectivity)

  • A C-based standard (Microsoft, 1992) — works with any language that can call C functions.
  • Uses a driver per DBMS (e.g., MySQL ODBC Driver, Oracle ODBC Driver, SQL Server ODBC Driver).
  • Widely used in Windows apps, Excel, and legacy systems.
  • Common in .NET (via System.Data.Odbc), Python (pyodbc), C/C++, and PowerShell.

2. JDBC (Java Database Connectivity)

  • Java's standard API for database access (part of JDK).
  • Uses a JDBC driver per DBMS (Type 4 drivers are pure-Java and most common).
  • Used by every Java/Kotlin/Scala app: Spring Boot, Hibernate, MyBatis, plain JDBC.

3. Other connectivity standards

  • ADO.NET — Microsoft's .NET data access layer.
  • DB-API (PEP 249) — Python's standard (psycopg2, mysql-connector-python, sqlite3).
  • PDO — PHP's data objects.
  • libpq — PostgreSQL's native C library.
  • Native drivers — MongoDB driver, Redis client, etc.

Diagram — ODBC/JDBC Architecture

Figure 6.2 — ODBC/JDBC: one API, many driver implementations

Syntax — JDBC and ODBC examples

Java — JDBC 
import java.sql.*;

public class JdbcExample {
    public static void main(String[] args) throws Exception {
        // 1. Load the driver (older JDBC; not needed in modern JDBC 4.0+)
        Class.forName("com.mysql.cj.jdbc.Driver");

        // 2. Connect
        Connection conn = DriverManager.getConnection(
            "jdbc:mysql://localhost:3306/companydb", "ali", "pass");

        // 3. Create a prepared statement (parameterized → safe)
        String sql = "SELECT Name, Salary FROM Employees WHERE DeptID = ?";
        PreparedStatement ps = conn.prepareStatement(sql);
        ps.setInt(1, 10);

        // 4. Execute and read results
        ResultSet rs = ps.executeQuery();
        while (rs.next()) {
            System.out.println(rs.getString("Name") + " earns " + rs.getDouble("Salary"));
        }

        // 5. Clean up
        rs.close(); ps.close(); conn.close();
    }
}
Python — ODBC (pyodbc) 
import pyodbc

# 1. Connect via ODBC (requires the DB's ODBC driver installed)
conn = pyodbc.connect(
    "DRIVER={MySQL ODBC 8.0 Driver};"
    "SERVER=localhost;DATABASE=companydb;UID=ali;PWD=pass;"
)

cursor = conn.cursor()

# 2. Parameterized query (safe from injection)
cursor.execute("SELECT Name, Salary FROM Employees WHERE DeptID = ?", 10)

for row in cursor.fetchall():
    print(f"{row.Name} earns {row.Salary}")

conn.close()
Simple Example

A Java Spring Boot app connects to MySQL using JDBC. A Python data script connects to the same MySQL server using pyodbc. Both speak the same SQL dialect — the only difference is the driver layer.

Real-Life Use Case

A banking dashboard written in .NET uses ODBC to query an old Oracle mainframe; the mobile app written in Java uses JDBC to query a new PostgreSQL cluster; both read the same Transactions data via their respective drivers. ODBC and JDBC are the "glue" that lets diverse apps share data.

6.3 Data Integrity — Entity, Referential, Domain Integrity

Definition

Data integrity refers to the accuracy, consistency, and reliability of data in the database. It ensures data is always valid, complete, and that relationships between tables are never broken. The DBMS enforces it via constraints.

Types of Integrity

1. Entity Integrity

  • Every row must be uniquely identifiable — that's the role of the Primary Key.
  • A primary key column cannot be NULL and cannot contain duplicates.
  • Ensures each row represents one distinct entity.

2. Referential Integrity

  • A Foreign Key in one table must reference an existing Primary Key in another (or be NULL).
  • Prevents orphan rows — you can't have an order without a customer.
  • Handled via FOREIGN KEY constraints with ON DELETE / ON UPDATE options.

3. Domain Integrity

  • Every column must contain values of the correct type, format, and range.
  • Enforced via data types (INT, VARCHAR, DATE), CHECK constraints, and NOT NULL.
  • Example: Age must be a positive integer; Email must contain @.

Additional categories:

  • User-defined integrity — business rules (e.g., "discount ≤ 50%").
  • Semantic integrity — logical meaning of the data is preserved.

Diagram — Three Types of Integrity

Figure 6.3 — Entity, Referential, and Domain integrity (all enforced by constraints)

Syntax — All three integrities in SQL

SQL — Integrity in action 
-- ENTITY INTEGRITY: Primary Key (unique + not null)
CREATE TABLE Customers (
    CustomerID INT PRIMARY KEY,
    Name       VARCHAR(100) NOT NULL
);

-- DOMAIN INTEGRITY: type, range, format
CREATE TABLE Employees (
    EmpID    INT PRIMARY KEY,
    Age      INT CHECK (Age >= 18 AND Age <= 100),    -- range
    Email    VARCHAR(150) CHECK (Email LIKE '%@%'),    -- format
    Salary   DECIMAL(10,2) CHECK (Salary > 0),         -- positive
    HireDate DATE                                      -- type enforced
);

-- REFERENTIAL INTEGRITY: foreign key
CREATE TABLE Orders (
    OrderID    INT PRIMARY KEY,
    CustomerID INT NOT NULL,
    Total      DECIMAL(10,2),
    FOREIGN KEY (CustomerID) REFERENCES Customers(CustomerID)
        ON DELETE RESTRICT          -- cannot delete a customer with orders
        ON UPDATE CASCADE           -- if customer ID changes, update orders too
);

-- This insert fails (referential integrity violation):
INSERT INTO Orders (OrderID, CustomerID, Total) VALUES (1, 99, 100);
-- ERROR: FK constraint fails (CustomerID 99 doesn't exist)

-- This also fails (domain integrity violation):
INSERT INTO Employees (EmpID, Age, Email, Salary) VALUES (1, 15, 'x@y.com', 50000);
-- ERROR: CHECK constraint 'Age >= 18' violated
Simple Example

Entity: Every order has a unique OrderID — no NULL, no duplicate.

Referential: Every order's CustomerID must exist in Customers.

Domain: A product's Price must be a positive number; a person's Age can't be negative.

Real-Life Use Case

In healthcare systems: entity integrity ensures each patient has a unique MRN (medical record number); referential integrity ensures every prescription references a real patient and a real doctor; domain integrity ensures a blood pressure reading is in a valid range (e.g., 60–250 systolic). Violations are rejected by the DBMS, protecting patient safety.

6.4 Constraints — PRIMARY KEY, FOREIGN KEY, UNIQUE, CHECK, NOT NULL

Definition

Constraints are rules declared on tables or columns that the DBMS automatically enforces. They're the mechanism used to implement data integrity (Topic 6.3). If a query would violate a constraint, the DBMS rejects it with an error.

Types of Constraints

Constraint Enforces Allows NULL? Per Table
PRIMARY KEY Unique row identifier ❌ No 1 only
FOREIGN KEY Referential integrity (row exists in parent) ✅ Yes (unless NOT NULL) Many
UNIQUE No duplicate values ✅ Yes (usually 1 NULL allowed) Many
CHECK Custom condition (range, format) ✅ Yes (evaluates to UNKNOWN) Many
NOT NULL Column always has a value ❌ No Many
DEFAULT Fallback value when none provided — Many

Diagram — Constraints on a Table

Figure 6.4 — Five constraints protecting different columns of the same table

Syntax — All five constraints in one table

SQL — All constraints 
-- Parent table first
CREATE TABLE Departments (
    DeptID   INT PRIMARY KEY,
    DeptName VARCHAR(100) NOT NULL
);

-- Child table with ALL five constraints
CREATE TABLE Employees (
    EmpID    INT           PRIMARY KEY,                          -- entity integrity
    Name     VARCHAR(100)  NOT NULL,                              -- never null
    Email    VARCHAR(150)  UNIQUE,                                -- no duplicates
    Age      INT           CHECK (Age >= 18 AND Age <= 100),      -- domain check
    Salary   DECIMAL(10,2) DEFAULT 30000 CHECK (Salary > 0),
    DeptID   INT,
    CONSTRAINT fk_emp_dept FOREIGN KEY (DeptID) REFERENCES Departments(DeptID)
        ON DELETE SET NULL                                       -- referential integrity
);

-- Named constraint (easier to drop later)
ALTER TABLE Employees
    ADD CONSTRAINT chk_email_domain CHECK (Email LIKE '%@%.%');

-- Add a UNIQUE constraint later
ALTER TABLE Employees
    ADD CONSTRAINT uq_email UNIQUE (Email);

-- Drop a constraint
ALTER TABLE Employees DROP CONSTRAINT chk_email_domain;

-- ---------- See all constraints on a table ----------
-- MySQL
SELECT CONSTRAINT_NAME, CONSTRAINT_TYPE, COLUMN_NAME
FROM information_schema.KEY_COLUMN_USAGE
WHERE TABLE_NAME = 'Employees';

-- PostgreSQL
SELECT conname, contype, pg_get_constraintdef(oid)
FROM pg_constraint
WHERE conrelid = 'employees'::regclass;

-- SQL Server
SELECT name, type_desc, is_disabled
FROM sys.check_constraints
WHERE parent_object_id = OBJECT_ID('Employees');
Simple Example

PRIMARY KEY: EmpID is unique and NOT NULL — every employee has one identity.

NOT NULL: Name can't be empty — every employee must have a name.

UNIQUE: Email must be unique — two employees can't share an email login.

CHECK: Age >= 18 — no child employees.

FOREIGN KEY: DeptID must match a real department.

Real-Life Use Case

A university student portal: StudentID is PK (unique), Name NOT NULL, CGPA CHECK 0.0–4.0, CourseID FK to Courses, and Email UNIQUE. When someone tries to enroll a ghost student or a 5.0 CGPA, the constraints reject the insert immediately.

6.5 Database Security — Authentication and Authorization

Definition

Database security is the set of mechanisms that protect the database from unauthorized access, misuse, and attacks. The two core layers are:

  • Authentication (AuthN) — proving who you are (username + password, certificate, Kerberos, multi-factor).
  • Authorization (AuthZ) — deciding what you can do once you're in (which tables, which operations).

Types / Methods

Authentication methods:

  • Password-based — username + password (default for most DBMSs).
  • Certificate-based — X.509 certificates for TLS mutual authentication.
  • Kerberos / Integrated Windows Auth — uses domain credentials (SQL Server, PostgreSQL).
  • LDAP / Active Directory — central user directory.
  • Multi-Factor Authentication (MFA) — password + token, or password + biometric.
  • Federated / OAuth / IAM — AWS IAM, Azure AD, GCP IAM for cloud databases.

Authorization methods:

  • Discretionary Access Control (DAC) — object owner grants/revokes (standard GRANT/REVOKE).
  • Mandatory Access Control (MAC) — labels (secret, classified) and clearance levels.
  • Role-Based Access Control (RBAC) — permissions assigned to roles, roles to users (Topic 6.6).
  • Attribute-Based Access Control (ABAC) — policies based on user/data attributes.

Diagram — AuthN vs AuthZ

Figure 6.5 — Authentication (who) then Authorization (what) — both required for access

Syntax — AuthN and AuthZ in SQL

SQL — Security in action 
-- AUTHENTICATION: create a user with a password
CREATE USER 'ali'@'localhost' IDENTIFIED BY 'Str0ngP@ss!';

-- Change password
ALTER USER 'ali'@'localhost' IDENTIFIED BY 'N3wP@ss!';

-- Require SSL for this user's connections (MySQL 8)
ALTER USER 'ali'@'localhost' REQUIRE SSL;

-- AUTHENTICATION via Kerberos (PostgreSQL)
CREATE USER ali WITH KERBEROS;
-- or via certificate:
CREATE USER ali WITH SSL CERTIFICATE;

-- AUTHORIZATION: grant specific privileges
GRANT SELECT ON SchoolDB.Students TO 'ali'@'localhost';
GRANT INSERT, UPDATE ON SchoolDB.Enrollments TO 'ali'@'localhost';
GRANT EXECUTE ON PROCEDURE SchoolDB.GiveRaise TO 'ali'@'localhost';

-- Deny specific action (SQL Server)
DENY DELETE ON SchoolDB.Students TO 'ali'@'localhost';

-- See what a user can do
SHOW GRANTS FOR 'ali'@'localhost';

-- See current user
SELECT USER(), CURRENT_USER();

-- Revoke everything (clean up)
REVOKE ALL PRIVILEGES, GRANT OPTION FROM 'ali'@'localhost';
Simple Example

Authentication: Ali types ali / Str0ngP@ss! — the DBMS verifies his password hash.

Authorization: Once logged in, Ali can SELECT from Students but cannot DELETE — because his user only has SELECT privilege.

Real-Life Use Case

In a hospital: nurses log in with smart cards (authentication via certificate). Once logged in, they can read patient vitals and write new measurements, but they cannot view billing data or delete records (authorization). Every action is logged for compliance. The system enforces both layers — a stolen password alone doesn't grant access if MFA is also required.

Never Store Passwords in Plain Text

The DBMS hashes passwords with strong algorithms (bcrypt, scrypt, Argon2, or SHA-256 with salt). Application code should also hash passwords before storing them in a Users table — never store plain passwords.

6.6 User Management and Role-Based Access Control

Definition

User management is the practice of creating, modifying, and removing database user accounts, and assigning them the right privileges. Role-Based Access Control (RBAC) is the best-practice model: instead of granting privileges to each user individually, you create roles (e.g., "read_only," "editor," "admin"), grant privileges to roles, and then assign roles to users.

Types of Access Control Models

  • DAC (Discretionary Access Control) — owner decides who gets access (GRANT/REVOKE).
  • RBAC (Role-Based Access Control) — access via roles. Preferred for teams.
  • MAC (Mandatory Access Control) — government/military labels. Very strict.
  • ABAC (Attribute-Based Access Control) — dynamic, based on user/data attributes (dept, region, time).

Benefits of RBAC

  • Scalability — 100 users × 5 roles = 5 grants instead of 500.
  • Consistency — everyone in a role has the same privileges.
  • Auditability — easy to see who has what by looking at role membership.
  • Least privilege — assign only the roles each user actually needs.
  • Easy revocation — revoke a role from a user, or remove a privilege from a role, and it applies to all affected users.

Diagram — RBAC Model

Figure 6.6 — RBAC: users assigned to roles, roles hold privileges

Syntax — Full RBAC setup

SQL — RBAC in action 
-- 1. Create roles (MySQL 8+ / PostgreSQL 14+)
CREATE ROLE read_only;
CREATE ROLE editor;
CREATE ROLE admin;

-- 2. Grant privileges to roles
GRANT SELECT ON SchoolDB.* TO read_only;
GRANT SELECT, INSERT, UPDATE, DELETE ON SchoolDB.* TO editor;
GRANT ALL PRIVILEGES ON SchoolDB.* TO admin;

-- 3. Create users
CREATE USER 'alice'@'localhost' IDENTIFIED BY 'Pass1!';
CREATE USER 'bob'@'localhost'   IDENTIFIED BY 'Pass2!';
CREATE USER 'carol'@'localhost' IDENTIFIED BY 'Pass3!';
CREATE USER 'dave'@'localhost'  IDENTIFIED BY 'Pass4!';

-- 4. Assign roles to users
GRANT read_only TO 'alice'@'localhost';
GRANT editor   TO 'bob'@'localhost';
GRANT editor   TO 'carol'@'localhost';
GRANT admin    TO 'dave'@'localhost';

-- 5. If a user changes job, just swap their role
REVOKE editor FROM 'bob'@'localhost';
GRANT read_only TO 'bob'@'localhost';

-- 6. See who has what role
SELECT user, host FROM mysql.user WHERE user IN ('alice','bob','carol','dave');
SHOW GRANTS FOR 'bob'@'localhost';

-- 7. Clean up when someone leaves
REVOKE ALL PRIVILEGES, GRANT OPTION FROM 'bob'@'localhost';
DROP USER 'bob'@'localhost';

-- ---------- PostgreSQL RBAC example ----------
CREATE ROLE read_only NOLOGIN;
GRANT CONNECT ON DATABASE school TO read_only;
GRANT USAGE ON SCHEMA public TO read_only;
GRANT SELECT ON ALL TABLES IN SCHEMA public TO read_only;

CREATE ROLE alice LOGIN PASSWORD 'Pass1!';
GRANT read_only TO alice;
Simple Example

Instead of granting SELECT to Alice, Bob, Carol, and Dave separately (4 grants), you:

1. Create role read_only → grant it SELECT once.

2. Assign Alice and Bob the read_only role.

3. When a new intern arrives, you grant read_only — done.

Real-Life Use Case

A SaaS company uses three roles: app_read (read-only, used by dashboards), app_write (read+write, used by the main app), app_admin (all privileges, used only by the ops team). As the team grows, new engineers just get app_admin — no need to re-grant each table privilege individually.

Principle of Least Privilege

Always grant the minimum privileges a role needs. If an attacker compromises app_read, they can only read — not modify or drop tables. The blast radius is small.

6.7 Encryption and Auditing

Definition

Encryption scrambles data so it can only be read by someone with the right key. Auditing keeps a record of every action (who did what, when, from where) so you can detect attacks, investigate incidents, and prove compliance.

Together, they form the defense-in-depth layer beyond authentication and authorization: even if an attacker gets a file or a backup, the data is unreadable (encryption), and their actions are recorded (auditing).

Types of Encryption

1. Encryption at rest — data stored on disk is encrypted:

  • Transparent Data Encryption (TDE) — whole database file encrypted; applications unaffected (SQL Server TDE, Oracle TDE, MySQL Enterprise).
  • Column-level encryption — specific sensitive columns (SSN, credit card) encrypted individually.
  • File-system encryption — BitLocker, LUKS, encrypted EBS volumes.

2. Encryption in transit — data on the network is encrypted:

  • TLS/SSL — every modern DBMS supports TLS connections.
  • VPN — for remote connectivity.
  • SSH tunnels — secure tunneling to a database port.

3. Encryption in use (advanced) — data is encrypted even while being processed:

  • Always Encrypted (SQL Server), homomorphic encryption (emerging).

Types of Auditing

  • Login auditing — track who logs in, when, from where.
  • Query/DML auditing — record every SELECT/INSERT/UPDATE/DELETE (or the sensitive ones).
  • Schema change auditing — log CREATE/ALTER/DROP events.
  • Trigger-based auditing — custom audit table populated by triggers.
  • Native auditing — built-in features like SQL Server Audit, Oracle Unified Auditing, MySQL Audit Plugin, PostgreSQL pgAudit.

Diagram — Defense in Depth

Figure 6.7 — Defense in depth: layered security with encryption and auditing at the core

Syntax — Encryption & auditing in SQL

SQL — Encryption 
-- ---------- Encryption in transit ----------
-- Require SSL for a user (MySQL)
ALTER USER 'ali'@'localhost' REQUIRE SSL;

-- Force TLS for all connections (PostgreSQL, in postgresql.conf)
-- ssl = on
-- ssl_cert_file = 'server.crt'
-- ssl_key_file = 'server.key'

-- ---------- Column-level encryption (MySQL 8) ----------
-- Insert encrypted value using AES_ENCRYPT with a key
INSERT INTO Patients (PatientID, SSN_encrypted)
VALUES (1, AES_ENCRYPT('123-45-6789', 'my-secret-key'));

-- Retrieve and decrypt
SELECT PatientID, AES_DECRYPT(SSN_encrypted, 'my-secret-key') AS SSN
FROM Patients;

-- ---------- SQL Server Always Encrypted ----------
-- (uses the SSMS wizard; column encryption keys stored separately)

-- ---------- Encryption at rest (MySQL/InnoDB) ----------
-- In my.cnf:
-- [mysqld]
-- early-plugin-load = keyring_file.so
-- keyring_file_data = /var/lib/mysql-keyring/keyring

CREATE TABLE Sensitive (
    ID INT PRIMARY KEY,
    Data VARCHAR(200)
) ENGINE=InnoDB ENCRYPTION='Y';   -- per-table encryption
SQL — Auditing 
-- ---------- Trigger-based audit (works on any DBMS) ----------
CREATE TABLE AuditLog (
    AuditID    BIGINT AUTO_INCREMENT PRIMARY KEY,
    TableName  VARCHAR(100),
    Action     VARCHAR(20),
    RowID      INT,
    ChangedBy  VARCHAR(100),
    ChangedAt  TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    OldValue   TEXT,
    NewValue   TEXT
);

DELIMITER $$
CREATE TRIGGER trg_salary_audit
AFTER UPDATE ON Employees
FOR EACH ROW
BEGIN
    IF OLD.Salary <> NEW.Salary THEN
        INSERT INTO AuditLog (TableName, Action, RowID, ChangedBy, OldValue, NewValue)
        VALUES ('Employees', 'UPDATE_SALARY', OLD.EmpID, USER(),
                CONCAT(OLD.Salary), CONCAT(NEW.Salary));
    END IF;
END$$
DELIMITER ;

-- Test it
UPDATE Employees SET Salary = 90000 WHERE EmpID = 1;
SELECT * FROM AuditLog;

-- ---------- Built-in auditing ----------
-- MySQL Enterprise Audit (plugin) — logs connections, queries, errors
INSTALL PLUGIN audit_log SONAME 'audit_log.so';

-- PostgreSQL pgAudit
CREATE EXTENSION pgaudit;
ALTER SYSTEM SET pgaudit.log = 'ddl, role';

-- SQL Server Audit
CREATE SERVER AUDIT MyAudit TO FILE (FILEPATH = 'D:\\Audit\\');
ALTER SERVER AUDIT MyAudit WITH (STATE = ON);
CREATE DATABASE AUDIT SPECIFICATION DbAudit
FOR SERVER AUDIT MyAudit
ADD (SELECT, INSERT, UPDATE, DELETE ON dbo.Employees BY PUBLIC);

-- ---------- See audit events ----------
SELECT * FROM mysql.audit_log_current_session;  -- MySQL
SELECT * FROM sys.fn_get_audit_file('D:\\Audit\\*', NULL, NULL);  -- SQL Server
Simple Example

Encryption: a customer's credit card number is stored as AES-encrypted ciphertext. Only the payment service (with the key) can decrypt it.

Auditing: every time a DBA modifies a salary, an automatic trigger records the old and new value, who made the change, and when — visible in the AuditLog table.

Real-Life Use Case

A bank must comply with PCI-DSS (payment card) and SOX (financial records). It encrypts all card numbers with column-level encryption, requires TLS for all DB connections, and keeps 7-year audit logs of who accessed which account. During an audit, the compliance team can prove "no unauthorized user has read customer X's data in 3 years" by querying the audit log.

Key Management is Critical

Encryption is only as strong as the key. Store keys in a dedicated key management service (AWS KMS, Azure Key Vault, HashiCorp Vault) — never in the application code, config files, or the same database as the encrypted data.

6.8 SQL Injection and Prevention Techniques

Definition

SQL Injection (SQLi) is one of the most dangerous web vulnerabilities. It happens when user input is concatenated directly into SQL strings, letting an attacker inject their own SQL commands. A successful SQLi can read, modify, or delete any data the application can access — often the entire database.

SQLi consistently ranks in the OWASP Top 10 (currently #3 in the 2021 list).

How It Works — A Vulnerable Example

VULNERABLE — DO NOT USE 
// VULNERABLE: user input is concatenated into SQL
String userInput = request.getParameter("username");
String sql = "SELECT * FROM Users WHERE Username = '" + userInput + "'";

// Normal input:  'ali'
//   → SELECT * FROM Users WHERE Username = 'ali'   ✓

// Attack input:  ' OR '1'='1' --
//   → SELECT * FROM Users WHERE Username = '' OR '1'='1' --'
//   → Returns ALL users! Bypasses login!

// Attack input:  '; DROP TABLE Users; --
//   → SELECT * FROM Users WHERE Username = ''; DROP TABLE Users; --'
//   → Deletes the entire Users table!

Types of SQL Injection

  • Classic / In-band SQLi — attacker uses the same channel to inject and retrieve results.
    • Error-based — uses error messages to leak schema info.
    • Union-based — combines malicious query results with legitimate ones using UNION.
  • Blind SQLi — attacker can't see results but infers them from behavior:
    • Boolean-based — ask true/false questions via conditions.
    • Time-based — use SLEEP(5) to detect queries.
  • Out-of-band SQLi — exfiltrates data via DNS/HTTP requests.
  • Second-order SQLi — payload is stored now, executed later (e.g., in a stored procedure).

Prevention Techniques (in order of importance)

  1. Parameterized queries / Prepared statements — ALWAYS use them. The #1 defense.
  2. Stored procedures with parameters — same effect when used correctly.
  3. Input validation — whitelist allowed values (defense in depth, not sufficient alone).
  4. Least privilege — app's DB user only needs SELECT/INSERT/UPDATE on specific tables, not DROP.
  5. WAF (Web Application Firewall) — blocks common attack patterns (defense in depth).
  6. Error handling — never show SQL errors to users (leaks schema).
  7. ORM frameworks — use Hibernate, JPA, Entity Framework with bound parameters.
  8. Regular security audits — check for injection points in code reviews.

Syntax — Vulnerable vs Safe

Java — Vulnerable 
// ❌ VULNERABLE — do NOT use string concatenation!
String sql = "SELECT * FROM Users WHERE Username = '" + userInput + "'";
Statement stmt = conn.createStatement();
ResultSet rs = stmt.executeQuery(sql);
// Attacker input: ' OR '1'='1' --
// → returns ALL rows → login bypassed
Java — SAFE (PreparedStatement) 
// ✅ SAFE — use PreparedStatement with ? placeholders
String sql = "SELECT * FROM Users WHERE Username = ?";
PreparedStatement ps = conn.prepareStatement(sql);
ps.setString(1, userInput);   // input is bound as data, never parsed as SQL
ResultSet rs = ps.executeQuery();
// Attacker input ' OR '1'='1' -- is treated as a literal string
// → no rows found → login denied
Python — SAFE (parameterized) 
import sqlite3

conn = sqlite3.connect('app.db')
cursor = conn.cursor()

# ❌ VULNERABLE
# cursor.execute(f"SELECT * FROM Users WHERE Username = '{user_input}'")

# ✅ SAFE — parameterized with ? placeholders
cursor.execute("SELECT * FROM Users WHERE Username = ?", (user_input,))
rows = cursor.fetchall()
PHP — SAFE (PDO prepared) 
<?php
// ✅ SAFE — PDO with bound parameters
$stmt = $pdo->prepare("SELECT * FROM Users WHERE Username = :username");
$stmt->execute([':username' => $userInput]);
$rows = $stmt->fetchAll();
?>
Node.js — SAFE (mysql2) 
// ✅ SAFE — mysql2 supports parameterized queries
const [rows] = await connection.execute(
    'SELECT * FROM Users WHERE Username = ?',
    [userInput]
);
SQL — Stored procedure (also safe) 
-- Stored procedure with parameters (safe)
DELIMITER $$
CREATE PROCEDURE FindUser(IN p_username VARCHAR(100))
BEGIN
    -- The parameter is bound, not concatenated
    SELECT * FROM Users WHERE Username = p_username;
END$$
DELIMITER ;

-- From application:
CALL FindUser('ali');
-- Even if 'ali' contains SQL, it's treated as a value, not code.
Simple Example

Attack: a login form has username field. Attacker enters ' OR '1'='1' --. Vulnerable SQL becomes SELECT * FROM Users WHERE Username = '' OR '1'='1' --' — returns all users → attacker is logged in as the first one.

Prevention: with a parameterized query, the input is bound as a literal string. The SQL becomes effectively SELECT * FROM Users WHERE Username = '\' OR \'1\'=\'1\' --' — no rows match, access denied.

Real-Life Use Case

Tesla, Sony, TalkTalk, British Airways, Equifax — all have suffered major breaches where SQL injection or related injection was a factor. In 2017, Equifax leaked 143 million records; injection flaws were part of the chain. Using prepared statements is a hard requirement in every security standard (PCI-DSS, HIPAA, SOC 2).

SQLi Rules to Live By
  • ✅ ALWAYS use parameterized queries / prepared statements.
  • ❌ NEVER concatenate user input into SQL strings — not even once.
  • ✅ Use ORM frameworks that handle this automatically.
  • ✅ Apply least privilege — app DB user should not have DROP/DELETE unless truly needed.
  • ✅ Use a WAF as defense in depth.
  • ❌ Never reveal SQL errors to end users — they leak schema info.
