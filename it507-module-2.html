2.1 Data Models — Definition and Importance

Definition

A data model is a collection of concepts, rules, and notations used to describe the structure of a database — how data is organized, how it relates to other data, what constraints apply, and what operations can be performed. Think of it as a blueprint or a language for describing data.

Why Data Models Are Important

  • Clarity — gives everyone (developers, DBAs, business) a shared vocabulary.
  • Structure — defines how data is organized and related before we build it.
  • Communication — acts as a contract between database designers and application developers.
  • Data independence — lets the physical storage change without breaking the logical design.
  • Validation — makes it easy to check that the design meets the business requirements.

Types of Data Models (Three Categories)

  1. Conceptual (High-level) Data Model — close to how users think; e.g., ER model. Used for requirements gathering.
  2. Logical (Representational) Data Model — describes structure without physical details; e.g., relational model (tables, keys).
  3. Physical (Low-level) Data Model — describes how data is actually stored on disk; e.g., indexes, file organization.

Diagram — Three Levels of Data Models

Figure 2.1 — Conceptual → Logical → Physical: from business ideas to disk storage
Simple Example

Conceptual: "A student can enroll in many courses, and a course can have many students." (ER model)

Logical: "Table Enrollment(student_id, course_id, grade) with composite primary key."

Physical: "Store rows in a B+ tree indexed on student_id; 8 KB pages on SSD."

Real-Life Use Case

A hospital designing a new patient system: doctors describe patient flows (conceptual), the DBA builds tables like Patients, Visits, Prescriptions (logical), and then tunes indexing and storage on SSDs for fast lookups (physical).

2.2 Object-Relational Data Model

Definition

The Object-Relational Data Model is a hybrid model that combines the traditional relational model (tables, rows, columns) with object-oriented features (user-defined types, inheritance, methods, complex objects). It is sometimes called extended relational.

Key Features / Types of Extensions

  • User-defined types (UDTs) — create custom types like Address, Phone, etc.
  • Complex / nested types — store arrays, sets, and nested objects inside columns.
  • Inheritance — types can inherit attributes from parent types.
  • Methods — attach functions to types to operate on their data.
  • Large objects (LOBs) — BLOB/CLOB for images, audio, large text.

Diagram — Hybrid Structure

Figure 2.2 — Relational table with object columns (UDT, array)

Syntax — PostgreSQL (classic object-relational DBMS)

PostgreSQL 
-- 1. Create a user-defined type
CREATE TYPE Address AS (
    street VARCHAR(100),
    city   VARCHAR(50),
    zip    VARCHAR(10)
);

-- 2. Use it as a column type inside a regular relational table
CREATE TABLE Customers (
    CustomerID  INT PRIMARY KEY,
    Name        VARCHAR(100),
    HomeAddress Address,
    Phones      VARCHAR(20)[]   -- array column
);

-- 3. Insert a row with nested object and array
INSERT INTO Customers VALUES (
    1,
    'Ali',
    ROW('Mall Road', 'Lahore', '54000')::Address,
    ARRAY['0300-1234567', '0321-7654321']
);

-- 4. Query a field inside the nested object
SELECT Name, (HomeAddress).city AS City FROM Customers;
Simple Example

Instead of splitting an address into street, city, zip columns, you store it as a single Address type. Cleaner design, easier reuse, but still stored inside a normal relational table.

Real-Life Use Case

A real-estate platform stores Property records where each property has an Address object, an array of ImageURLs, and a nested GeoLocation(lat, lng). PostgreSQL's object-relational features handle this natively without extra tables.

2.3 Object-Oriented Data Model

Definition

The Object-Oriented Data Model (OODM) stores data as objects — just like objects in OOP languages (Java, C++). Each object bundles state (attributes) and behavior (methods). Objects belong to classes, and classes can inherit from parent classes.

Key Concepts

  • Object — an instance of a class holding data + methods.
  • Class — template defining attributes and methods.
  • Encapsulation — hide internal details, expose only methods.
  • Inheritance — subclass inherits from superclass.
  • Polymorphism — same method behaves differently per class.
  • Object Identity (OID) — each object has a unique internal ID, independent of its attributes.

Diagram — Class Hierarchy

Figure 2.3 — Student and Teacher inherit from Person

Syntax — Java example with db4o-style OODBMS

Java (Object-Oriented) 
// Parent class
class Person {
    String name;
    int age;
    String email;

    void displayInfo() {
        System.out.println(name + " (" + age + ")");
    }
}

// Child class — inherits Person
class Student extends Person {
    String rollNo;
    double cgpa;

    void calculateGrade() {
        if (cgpa >= 3.5) System.out.println("A");
        else if (cgpa >= 3.0) System.out.println("B");
        else System.out.println("C");
    }
}

// Creating and storing objects (in an OODBMS like db4o)
Student s = new Student();
s.name = "Ali";
s.rollNo = "CS-101";
s.cgpa = 3.7;
db.store(s);   // store the object directly — no tables needed
s.displayInfo();
Simple Example

A Student object holds its data (name, rollNo, cgpa) and its method (calculateGrade()). The database stores it as one object — no need to flatten it into tables.

Real-Life Use Case

CAD/CAM software (AutoCAD), AI models, and multimedia editing tools use OODBMS to store complex graphics objects — each object retains its behavior and can be reconstructed exactly as it was created. ObjectDB and db4o are common choices.

2.4 Hierarchical Data Model

Definition

The Hierarchical Data Model organizes data in a tree structure. Each parent record can have many child records, but each child has exactly one parent. It was one of the first database models (used by IBM IMS in the 1960s) and is still used in some legacy systems.

Characteristics

  • One-to-many relationships only — no many-to-many directly (requires duplication).
  • Root record at the top; every record except the root has exactly one parent.
  • Fast traversal — following a path from root to leaf is quick.
  • Rigid structure — hard to modify without rebuilding the whole tree.
  • Redundancy — same data may repeat in multiple branches.

Diagram — Tree Structure

Figure 2.4 — Company → Departments → Employees (tree hierarchy)

Syntax — JSON representation (tree-friendly)

JSON (Hierarchical structure) 
{
  "Company": "TechCorp",
  "Departments": [
    {
      "DeptName": "Sales",
      "Employees": [
        { "EmpID": 101, "Name": "Ali",  "Salary": 50000 },
        { "EmpID": 102, "Name": "Sara", "Salary": 55000 }
      ]
    },
    {
      "DeptName": "IT",
      "Employees": [
        { "EmpID": 201, "Name": "Bilal", "Salary": 70000 },
        { "EmpID": 202, "Name": "Hina",  "Salary": 68000 }
      ]
    }
  ]
}
Simple Example

A file system is hierarchical: /home/user/documents/report.pdf. Each folder has one parent, and can contain many children — exactly how the hierarchical model works.

Real-Life Use Case

Legacy banking systems (IBM IMS), organization charts, XML/JSON file trees, and Windows registry all follow the hierarchical model. Bill-of-materials in manufacturing is also a classic hierarchical use case — one product contains many sub-parts, each with its own sub-parts.

2.5 Network Data Model

Definition

The Network Data Model is an extension of the hierarchical model that allows many-to-many relationships. It uses a graph structure where records are connected via sets (pointers). Unlike hierarchical, a child record can have more than one parent. Developed by CODASYL in the 1970s.

Key Concepts

  • Record — similar to a table row, holds fields.
  • Set — a named relationship between an owner record and member records (1:N).
  • Owner — the "one" side of a set.
  • Member — the "many" side (can be a member in multiple sets).
  • Pointers — physical links connecting records directly (fast but rigid).

Diagram — Network of Records

Figure 2.5 — Students ↔ Courses: many-to-many network relationships

Syntax — Conceptual CODASYL-style pseudocode

CODASYL DDL (pseudo) 
-- Record definitions
RECORD Student
    FIELD StudentID   PIC 9(4)
    FIELD Name        PIC X(50)

RECORD Course
    FIELD CourseID    PIC 9(4)
    FIELD Title       PIC X(80)

-- Set: Enrollment — owner = Student, member = Course
SET Enrollment
    OWNER  Student
    MEMBER Course

-- A Student can enroll in many Courses (set membership)
-- A Course can be a member of many Student sets → many-to-many!
Simple Example

Ali is enrolled in Database and OS. Sara is enrolled in Database and Math. The network model stores these links as pointers, so moving from Ali → his courses → back to other students in those courses is very fast.

Real-Life Use Case

Airline reservation systems of the 1970s–90s (IBM IDMS) modeled flights, passengers, and seats as a network. Modern graph databases (Neo4j, Amazon Neptune) are spiritual successors — social networks, recommendation engines, and fraud detection all use graph relationships.

2.6 Relational Data Model

Definition

The Relational Data Model, proposed by E.F. Codd in 1970, stores data in tables (relations) consisting of rows (tuples) and columns (attributes). Relationships between tables are represented by shared column values (keys), not pointers. It is the most widely used model today (MySQL, Oracle, PostgreSQL, SQL Server).

Key Concepts

  • Relation / Table — a set of tuples (rows).
  • Tuple / Row — one record.
  • Attribute / Column — one field with a defined domain (data type).
  • Primary Key (PK) — uniquely identifies each row.
  • Foreign Key (FK) — references the PK of another table, creating relationships.
  • Candidate Key — any column(s) that could serve as PK.
  • Domain — the set of allowed values for an attribute.
  • Relational Integrity — entity integrity (no NULL PK) + referential integrity (FK must match an existing PK).

Diagram — Two Related Tables

Figure 2.6 — Two relational tables linked by a foreign key

Syntax — Creating relational tables with keys

SQL 
-- Parent table (Students) with a primary key
CREATE TABLE Students (
    StudentID INT PRIMARY KEY,
    Name      VARCHAR(100) NOT NULL
);

-- Child table (Enrollments) with a foreign key
CREATE TABLE Enrollments (
    StudentID INT NOT NULL,
    CourseID  INT NOT NULL,
    PRIMARY KEY (StudentID, CourseID),
    FOREIGN KEY (StudentID) REFERENCES Students(StudentID)
        ON DELETE CASCADE
);

-- Insert data
INSERT INTO Students VALUES (1, 'Ali'), (2, 'Sara');
INSERT INTO Enrollments VALUES (1, 503), (1, 507), (2, 503);

-- Join to get meaningful output
SELECT s.Name, e.CourseID
FROM Students s
JOIN Enrollments e ON s.StudentID = e.StudentID;
Simple Example

The Enrollments table says "student 1 is enrolled in courses 503 and 507." The foreign key StudentID guarantees that every enrollment refers to a real student — no orphan enrollments possible.

Real-Life Use Case

Almost every business system uses relational databases: banking (accounts ↔ transactions), e-commerce (orders ↔ customers ↔ products), ERP systems (SAP, Oracle), and medical records (patients ↔ visits ↔ prescriptions). It's the workhorse of modern data management.

2.7 Comparison of Data Models

Definition

Each data model has different strengths and weaknesses. Choosing the right one depends on the application's complexity, data relationships, performance needs, and how often the schema changes.

Detailed Comparison Table

Model Structure Relationships Pros Cons Best For
Hierarchical Tree 1:N only Simple, fast traversal No M:N, rigid, redundant File systems, org charts
Network Graph of records M:N via sets Handles complex relationships Very complex, pointer-based Legacy airline/telecom systems
Relational Tables (rows/cols) Via foreign keys Mathematically sound, flexible, SQL standard Not ideal for deep hierarchies or objects Most business apps
Object-Oriented Objects & classes Direct references Natural for OOP, complex data No universal query standard CAD, multimedia, AI
Object-Relational Tables + objects FK + object refs Best of both worlds Complex implementation Modern apps needing both

Diagram — Evolution Timeline

Figure 2.7 — Historical evolution of data models
How to Choose
  • Simple 1:N data (file paths, org charts) → Hierarchical
  • Complex M:N links (networks, social graphs) → Network or Graph DB
  • Structured business data (banking, ERP, e-commerce) → Relational
  • Complex nested data with methods (CAD, multimedia) → Object-Oriented
  • Both structured & complex (modern web apps) → Object-Relational
Real-Life Use Case

A CRM might use Relational for customers/orders, but store an entire Object-Relational XML document for each custom form. Large social networks may use a hybrid of Relational + Graph. The right choice depends on the workload.

2.8 Schema Design — Conceptual, Logical, and Physical

Definition

Schema means the structure or blueprint of a database — what tables (or entities) exist, their columns, data types, relationships, and constraints. Schema design happens at three levels, moving from business requirements to physical implementation.

Three Schema Levels

1. Conceptual Schema (High-level)

  • Focus: what data we need — business view.
  • Tools: ER diagrams, entity lists, business rules.
  • Audience: business analysts and end users.
  • No details about data types, keys, or storage.

2. Logical Schema (Mid-level)

  • Focus: tables, columns, data types, primary/foreign keys, constraints.
  • Tools: Relational model, normalized tables.
  • Audience: DBAs and developers.
  • Database-independent (same logical design for MySQL or Oracle).

3. Physical Schema (Low-level)

  • Focus: how data is actually stored — indexes, partitions, filegroups, compression.
  • Tools: DBMS-specific DDL, storage config.
  • Audience: DBA only.
  • DBMS-specific (differs by platform).

Diagram — Three Levels with Examples

Figure 2.8 — Same database described at three different levels

Syntax — Logical and Physical side by side

SQL — Logical Schema 
-- LOGICAL: tables, keys, relationships (DBMS-independent)
CREATE TABLE Students (
    StudentID INT PRIMARY KEY,
    Name      VARCHAR(100) NOT NULL
);

CREATE TABLE Enrollments (
    StudentID INT,
    CourseID  INT,
    PRIMARY KEY (StudentID, CourseID),
    FOREIGN KEY (StudentID) REFERENCES Students(StudentID)
);
SQL — Physical Schema (MySQL-specific) 
-- PHYSICAL: storage, indexes, engine, compression
CREATE TABLE Students (
    StudentID INT PRIMARY KEY,
    Name      VARCHAR(100) NOT NULL
) ENGINE = InnoDB
  DEFAULT CHARSET = utf8mb4
  ROW_FORMAT = COMPRESSED;

-- Add an index for faster lookups by name
CREATE INDEX idx_students_name ON Students(Name);

-- Partition data by enrollment year (MySQL example)
ALTER TABLE Enrollments
    PARTITION BY HASH(StudentID) PARTITIONS 4;
Simple Example

Conceptual: "Students enroll in courses." (one line!)
Logical: Two tables with a foreign key.
Physical: InnoDB engine, compressed rows, B+ tree index on name, hash-partitioned by StudentID.

Real-Life Use Case

A bank's design team: business analysts draw the conceptual ER model (accounts ↔ customers ↔ transactions). DBAs translate it into logical normalized tables. Then the physical DBA tunes for production — partitioning large transaction tables by year, creating clustered indexes on account_id, and enabling compression on historical data.

2.9 Entity-Relationship (ER) Modeling

Definition

Entity-Relationship (ER) modeling is a conceptual design technique that represents the data requirements of a system as entities, their attributes, and the relationships between them. Introduced by Peter Chen in 1976. An ER diagram (ERD) is the visual output — the most common tool for database design.

Key Components

  • Entity — a thing (Student, Course, Order). Drawn as a rectangle.
  • Attribute — a property of an entity (Name, Age). Drawn as an oval.
  • Primary Key — attribute that uniquely identifies an entity (underlined).
  • Relationship — how two entities connect (Enrolled). Drawn as a diamond.
  • Cardinality — how many instances relate: 1:1, 1:N, M:N.
  • Participation — total (must) or partial (may).
  • Weak Entity — cannot exist without its parent (double rectangle).

Diagram — ER Diagram for Student & Course

Figure 2.9 — ER diagram with entities, attributes, relationship, and cardinality

Syntax — Converting ER to relational tables

SQL — Result of ER → relational mapping 
-- 1. Each strong entity becomes a table
CREATE TABLE Students (
    StudentID INT PRIMARY KEY,
    Name      VARCHAR(100)
);

CREATE TABLE Courses (
    CourseID INT PRIMARY KEY,
    Title    VARCHAR(200)
);

-- 2. A M:N relationship becomes its own table
--    with FKs to both sides + any relationship attributes
CREATE TABLE Enrollments (
    StudentID INT,
    CourseID  INT,
    Grade     CHAR(2),
    PRIMARY KEY (StudentID, CourseID),
    FOREIGN KEY (StudentID) REFERENCES Students(StudentID),
    FOREIGN KEY (CourseID)  REFERENCES Courses(CourseID)
);
Simple Example

Think of any real-world scenario: Hospital (Patient, Doctor, Visit), Library (Book, Member, Loan), Airline (Flight, Passenger, Booking). Each becomes a set of entities, and their connections become relationships.

Real-Life Use Case

Before building any database, an ER diagram is drawn. For example, an e-commerce site's ER diagram has entities Customer, Order, Product, Payment, connected with relationships places, contains, pays_via. The DBA then converts each entity → table and each relationship → foreign key or join table.

2.10 Normalization (1NF, 2NF, 3NF, BCNF)

Definition

Normalization is the process of organizing columns and tables to reduce redundancy and eliminate data anomalies (insert, update, delete anomalies). It works step-by-step through a series of "normal forms" (1NF → 2NF → 3NF → BCNF), each stricter than the last.

Why Normalize? (Anomalies Without It)

  • Insert anomaly — can't add a new course without a student enrolling (in an unnormalized table).
  • Update anomaly — a student's name appears in 50 rows; updating one means updating all 50.
  • Delete anomaly — deleting the last enrollment for a course also deletes the course itself.

The Four Main Normal Forms

1NF (First Normal Form) — Atomic values

  • Every cell must contain a single, atomic value.
  • No repeating groups, no arrays or lists in a cell.
  • Each row must be unique (needs a primary key).

2NF (Second Normal Form) — No partial dependencies

  • Must be in 1NF.
  • Every non-key attribute must depend on the whole primary key, not just part of it (relevant only if the PK is composite).

3NF (Third Normal Form) — No transitive dependencies

  • Must be in 2NF.
  • No non-key attribute depends on another non-key attribute. Every non-key attribute depends only on the primary key.

BCNF (Boyce-Codd Normal Form) — Every determinant is a candidate key

  • Stricter version of 3NF.
  • Every determinant (attribute on the left side of a functional dependency) must be a candidate key.
  • Handles some edge cases that 3NF misses.

Diagram — Normalization Steps

Figure 2.10 — Normalization path: UNF → 1NF → 2NF → 3NF → BCNF

Syntax — Step-by-step normalization example

Step 0 — Unnormalized (bad!) — array in one cell:

UNF (Bad) 
-- Unnormalized: courses column holds a comma-separated list!
| StudentID | Name | Courses           | DeptName |
|-----------|------|-------------------|----------|
| 1         | Ali  | DB, OS, Math      | CS       |
| 2         | Sara | DB, Networking    | CS       |

Step 1 — 1NF (atomic values, no lists):

1NF 
-- 1NF: split the list into separate rows
CREATE TABLE Students_1NF (
    StudentID INT,
    Name      VARCHAR(100),
    Course    VARCHAR(50),
    DeptName  VARCHAR(50),
    PRIMARY KEY (StudentID, Course)   -- composite PK
);

| StudentID | Name | Course     | DeptName |
|-----------|------|------------|----------|
| 1         | Ali  | DB         | CS       |
| 1         | Ali  | OS         | CS       |
| 1         | Ali  | Math       | CS       |
| 2         | Sara | DB         | CS       |
| 2         | Sara | Networking | CS       |

Step 2 — 2NF (remove partial dependency) — Name depends only on StudentID, not on the full composite key:

2NF (split into two tables) 
-- Students table: Name depends on StudentID only
CREATE TABLE Students (
    StudentID INT PRIMARY KEY,
    Name      VARCHAR(100)
);

-- Enrollments table: links students to courses
CREATE TABLE Enrollments (
    StudentID INT,
    Course    VARCHAR(50),
    DeptName  VARCHAR(50),
    PRIMARY KEY (StudentID, Course),
    FOREIGN KEY (StudentID) REFERENCES Students(StudentID)
);

Step 3 — 3NF (remove transitive dependency) — DeptName depends on Course, not on the full key:

3NF (final — clean design) 
-- 1. Students
CREATE TABLE Students (
    StudentID INT PRIMARY KEY,
    Name      VARCHAR(100)
);

-- 2. Courses: DeptName now depends on CourseID only
CREATE TABLE Courses (
    CourseID  VARCHAR(50) PRIMARY KEY,
    DeptName  VARCHAR(50)
);

-- 3. Enrollments: pure link table (no data duplication)
CREATE TABLE Enrollments (
    StudentID INT,
    CourseID  VARCHAR(50),
    PRIMARY KEY (StudentID, CourseID),
    FOREIGN KEY (StudentID) REFERENCES Students(StudentID),
    FOREIGN KEY (CourseID)  REFERENCES Courses(CourseID)
);

Step 4 — BCNF — the above example already satisfies BCNF. BCNF matters for rare edge cases like when a table has multiple overlapping candidate keys:

BCNF edge-case example 
-- Suppose: a Student can take each Course with only ONE Teacher,
-- and each Teacher teaches only ONE Course.
-- Functional dependencies:
--   (Student, Course) -> Teacher
--   Teacher -> Course    <-- violates BCNF (Teacher is not a candidate key)

-- BCNF fix: split so every determinant is a candidate key
CREATE TABLE Teacher_Course (
    Teacher  VARCHAR(100) PRIMARY KEY,
    Course   VARCHAR(50)
);

CREATE TABLE Student_Teacher (
    StudentID INT,
    Teacher   VARCHAR(100),
    PRIMARY KEY (StudentID, Teacher),
    FOREIGN KEY (StudentID) REFERENCES Students(StudentID),
    FOREIGN KEY (Teacher)   REFERENCES Teacher_Course(Teacher)
);
Simple Example

1NF: Don't store "DB, OS, Math" in one cell — split into 3 rows.

2NF: Don't store student Name in every enrollment row — it depends only on StudentID.

3NF: Don't store DeptName next to CourseID — DeptName depends on CourseID, not on the composite key.

BCNF: Every determinant in the table must be a candidate key — fixes edge cases 3NF misses.

When NOT to Normalize

Sometimes over-normalization hurts read performance (too many joins). In data warehouses and reporting systems, we intentionally denormalize (combine tables, allow some redundancy) to speed up queries. The rule of thumb: normalize for OLTP, denormalize for OLAP.

Real-Life Use Case

An e-commerce database might store Orders and OrderItems separately (3NF). But its reporting warehouse might have a single flattened SalesFact table with product name, category, and customer details baked in — that's intentional denormalization to answer analytics queries in milliseconds instead of joining 10 tables.
